## Status contract with the R-03 browser client (the critical part)
The client (`lib/capture/retry.ts` `classifyUploadResult`, consumed by `lib/capture/browser/engine.ts` pump)
treats each outcome as: `200/201` done · `429` or `≥500` retry, bounded by 6 attempts then DROP ·
network failure retry forever (pruned only by the 10-min queue cap) · **every other 4xx DROP at once**.
So the route's status decides whether a segment is kept or lost. **Rule: an upstream/dependency failure is
always retryable (503); only a caller-caused problem is a 4xx.**

| Outcome | Status | Client does |
|---|---|---|
| Transcribe transient or any failure (model 5xx/429/timeout/400) | **503** | retry (bounded) |
| Redaction / DLP failure, DLP unavailable (fail closed, nothing stored) | **503** | retry (bounded) |
| Model returns EMPTY text (silence / non-speech) | **200**, store `lines: []` | done |
| Duplicate (already stored) | **200**, no model call | done |
| Oversized | 413 | drop |
| Path device ≠ credential | 403 | drop |
| Bad or missing token / unpaired | 401 | drop |
| Wrong `Content-Type` (checked BEFORE reading the body or any model call) | 400 | drop |
| Infra hiccup in auth lookup (Firestore outage) | stays a raw error → 500 via `handleApiError` | retry (bounded) |
Never wrap an infra failure as 401/403/422. Everything goes through `handleApiError`. Do not reuse
`ConflictError` (409) for duplicates. Known gap for the README: a backend outage longer than ~2 min drops
segments client-side (6 retries, backoff capped at 30 s), visible only as the client's `droppedCount`.

## Decisions (from the design review)
- **Idempotency:** check-then-create, no lease. A rare concurrent duplicate costs one extra model call and
  cannot double-store. Rejected: a claim/lease doc (needs a `status` field and expiry logic; not worth it).
- **Line granularity:** sync mode returns no utterance timestamps, so a ≤ 15 s segment becomes one or a few
  lines over `[0, duration]`. R-05's thread builder must not assume fine line times.
- **Build order:** ONE developer, sequential, TDD (about 4 h; three parallel agents cost more in
  coordination than they save). If fanning out, freeze slice 0 first; merge order 0 → 3 → 1 → 2 → 4 → 5 → 6.
- **Cut order if it slips:** smoke script → `+62/08` regex pass → custom vocabulary (ship auto-detect with
  an empty vocabulary). Core that cannot be cut: idempotent route + transcribe + fail-closed redaction + store.
- Out of scope: Cloud Tasks hand-off to the next pipeline step (nothing consumes it until R-05a/b).

**Tech-lead review (round 1): CHANGES REQUESTED.** No hard-rule violations, but:
- **[major]** The route's own test file had two `expect(true).toBe(true)` placeholders standing in
  for the route's critical behaviour (ordering, status mapping) — "278/278 passing" did not actually
  prove the route worked.
- **[major]** The whitelisted debug log on transcribe/redact failure was cosmetic: it always logged
  the literal string `"ServiceUnavailableError"`, with no way to tell a 429 from a timeout from an
  outage, because nothing upstream preserved the real cause.
- **[minor]** Device-match (403) ran after the full request body was read into memory, not before, as

- **[minor]** Unbounded `start_ms`/`end_ms` could throw a raw `RangeError` post-transcribe → 500 → 6
  wasted paid retries on an unrecoverable request.
- **[minor]** Inconsistent 400 vs 422 on the same validation failure; a missing header silently
  coerced to epoch 0 instead of being rejected.
- **[minor]** The success response returned the full stored segment, including redacted transcript
  text, to the shop device — a data-minimisation gap, not a hard-rule breach.

**Fix round** (`dcb79ae` through `cc20320`, 16 commits): `ServiceUnavailableError` gained optional

the success response minimised to `{ seg_id, lines: <count> }`; the two placeholder tests replaced
