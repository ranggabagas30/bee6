## 0. Findings and blockers (read first)

1. **No blocker.** Everything R-09 builds on is merged: `ProposalSchema` / `ConstraintSchema`
   (`lib/firestore/schema.ts`), `toProposalView` (`lib/proposals/view.ts`), `createConstraint`
   (`lib/constraints/service.ts`), `/proposals` with `ProposalCard`, `ConstraintsPanel` and `ProposalsApp`
   (`app/proposals/*`), and `authedGetJson` / `authedPostJson` accepting 200 and 201 (`lib/auth/client/api.ts`).
2. **`ProposalSchema` has nowhere to store a decision (found in the code).** It is `.strict()` and has no field for
   who decided, when, why, or which constraint a rejection produced. R-08 reserved the three statuses
   (`awaiting_owner`, `approved`, `rejected`) but not the decision data. R-09 must add **two optional fields**
   (`supervisor_review`, `owner_decision`) plus status/decision invariants (Task 1). This is **additive, not a
   redesign** (inherited item 1): no existing field changes, every R-08-era doc (which lacks both keys) still
   parses, and `generateProposal` is not touched by it. `.optional()` is required, not just `.nullable()`, because
   demo Firestore already holds R-08 QA docs without the keys.
3. **The freshness check lives inline in R-08's commit transaction** (`service.ts` step 8f:
   `t !== undefined && t.status === "fact" && t.excluded_from_evidence !== true && t.label_source !== "supervisor_rejected"`).
   Inherited item 5 says "the **same** freshness check". To guarantee "same", R-09 extracts that predicate into
   `lib/proposals/freshness.ts` and R-08's commit calls it (a one-line swap; R-08's own tests prove it unchanged).
4. **`createConstraint` runs its own Firestore transaction** and its redaction (SDP) is an async network call that
   cannot sit inside a Firestore transaction. So "reject + save constraint" cannot be one transaction without
   rewriting `createConstraint`, which inherited item 6 forbids ("never a second write path"). Decision (§1
   "Supervisor Reject ordering"): **pre-check → `createConstraint` → decision transaction**, idempotent on retry.
   The one leftover race (two supervisors deciding the same proposal within the same second) can leave a valid
   constraint whose rejection lost the race; it stays a real supervisor-written rule. Named in E20, accepted.
5. **R-08's constraint-aware regeneration creates parallel open proposals for one range** (by design, R-08 E31: a
   new constraint makes Generate run fresh instead of reusing, and the old proposal is "left exactly as it is"). With
   no way to clear the old one except *Reject*, and every supervisor reject reason becoming a **permanent**
   constraint (T-507), a supervisor would have to type a junk constraint ("superseded") into every future prompt
   just to tidy the list. R-09 therefore derives **"superseded"** in plain code (no new status, no write): an open
   proposal is superseded when a newer proposal for the **identical** range is open or approved. Superseded cards
   show a notice and no buttons; the decision routes refuse them (409 `SUPERSEDED`). §11 Q-2 lets Rangga overturn.
6. **"Cost/brand impact" on the owner's Approvals screen (web spec §4.4) has no data.** `ProposalContentSchema` has
   no such field and the ProposalAgent does not produce one. Adding it means a prompt + wire-schema + gate change to
   merged R-08 code. Not built; the owner sees the same card as the supervisor (change, rubric, metric, failure
   condition, review date, dated summaries). §11 Q-4.
7. **Known limit (inherited item 9):** an outlet with no supervisor account cannot move any proposal past
   `awaiting_supervisor`, owner-generated ones included. Both seeds create a supervisor; some ad-hoc test paths
   (owner-only accounts) do not. Not fixed here; the owner's card says "Waiting for supervisor review".
8. **Demo exposure, for R-12 (not built here):** judges using "Try as Supervisor" can reject with any text, and that
   text becomes a permanent constraint in the demo outlet (no edit/delete in MVP 1, R-08 E37). The same already holds
   for R-08's manual constraint field. R-12 needs a demo reset/re-seed of `constraints` and `proposals`. Recorded in §8.

**Effort: 6.9 h** (backlog 4 h; R-08 §9 projected 3.25 h after `createConstraint` reuse; v2 adds +0.4 h for Q-1 =
yes). Why it is larger, and the cut list, in §9.

## 1. Architecture (decisions and why)

**Same split as R-06/R-08: pure planner, thin service, thin store, thin route.**
- `lib/proposals/review-plan.ts`: pure `classifyDecision` + `buildDecisionWrite` + `supersededIds`. No I/O. Same
  pattern as R-06's `planConfirm` (`lib/day/confirm-service.ts`): it runs **inside** the store's transaction on a
  fresh snapshot, so every terminal state is re-derived, never assumed from a pre-read.
- `lib/proposals/review-service.ts`: `listProposals` and `decideProposal` (permission, outlet, redaction,
  `createConstraint` call, transaction, logging).
- `lib/firestore/proposal-review-store.ts`: a **new** store interface, not an extension of R-08's `ProposalStore`
  (extending it would force R-08's test fakes to implement methods they never use).
- Three routes: `GET /api/v1/proposals`, `POST /api/v1/proposals/{id}/review` (supervisor),
  `POST /api/v1/proposals/{id}/approve` (owner). Route names are the web spec §6.2 row, verbatim.

**State machine (the only legal moves; everything else is a 409):**
```
awaiting_supervisor ──supervisor Feasible──► awaiting_owner ──owner Approve──► approved   (R-10 then writes SOP vN+1)
        │                                         │
        └──supervisor Reject (+constraint)──► rejected ◄──owner Reject──┘
suppressed / blocked: no moves (409 NOT_REVIEWABLE)
```
- `proposals:review` stays supervisor-only; `proposals:approve` stays owner-only (`lib/auth/rbac.ts`, unchanged
  for these two). The review route can only produce `awaiting_owner` or `rejected`; the approve route can only act on
  `awaiting_owner`. There is no code path from any status to `approved` except the owner's route on
  `awaiting_owner`, and `awaiting_owner` is only reachable through the supervisor's Feasible. That is "nothing ships
  without both approvals" by construction, plus a schema invariant (Task 1: `approved` requires
  `supervisor_review.decision === "feasible"`).
- **Approval sequence ignores who generated** (inherited item 3, R-08 Q-10). `classifyDecision` takes no
  `requested_by_role` input at all.

**Rule order in `classifyDecision` (precedence; first match wins; pinned by tests 4.T14):**
1. Proposal missing, malformed, or another outlet's → `not_found` (404; existence is never revealed).
2. `status ∈ {suppressed, blocked}` (or `content === null`) → `NOT_REVIEWABLE`.
3. **Idempotency:** the same actor's same decision already stands → `unchanged` (200). Checked before every
   freshness rule so a double tap never turns into a confusing 409.
4. **Stage:** supervisor needs `awaiting_supervisor` (else `ALREADY_DECIDED`). Owner: `awaiting_supervisor` →
   `NOT_YET_REVIEWABLE`; anything else but `awaiting_owner` → `ALREADY_DECIDED`.
5. Superseded (§0 item 5) → `SUPERSEDED`.
6. A **reject** proceeds here. Stale evidence, a changed SOP or a late constraint never block a rejection: refusing
   a "no" is never safer than accepting it.
7. Positive decisions only (Feasible, Approve): evidence no longer holds → `EVIDENCE_STALE`; current SOP version ≠
   the proposal's `generator.sop_version_id` → `SOP_CHANGED`; a constraint exists that the proposal did not
   acknowledge and the request did not acknowledge → `CONSTRAINT_ADDED`.
8. Proceed.

**Late constraints (inherited item 7), decided: allow with explicit acknowledgement, enforced on the server.**
- `late = current constraint ids − proposal.content.constraint_ids_acknowledged` (computed in the transaction).
- The card lists each late constraint's text with the notice "Added after this proposal was made". The
  Feasible/Approve confirm step shows a required checkbox "I checked this proposal against the constraints above".
- The request carries `acknowledged_constraint_ids: uuid[]`. The server refuses (409 `CONSTRAINT_ADDED`, nothing
  written) unless **every** late id is in it. Ids, not a boolean, so a constraint added between page load and tap is
  never silently acknowledged; the client reloads and the new one appears.
- The decision stores exactly `late` as `acknowledged_constraint_ids` (extra ids in the request are ignored).
- The owner acknowledges independently: owner `late` is computed against the proposal's own
  `constraint_ids_acknowledged`, not against the supervisor's acknowledgement (the owner is the final check).
- **Why not block:** blocking would strand the proposal (no supersede status in R-08's enum; rejecting it would
  write a junk permanent constraint, §0 item 5). Regenerating remains one tap and is the card's suggested path; the
  supervisor and owner judge, as R-08 §9 item 7 proposed. Rangga may overturn (§11 Q-3); the change is one branch.

**SOP changed (tech-lead addition, cheap insurance for R-10).** A proposal targets a step of a specific SOP version
(`generator.sop_version_id`). Once R-10 ships SOP v2, an older open proposal may point at a step that changed or
disappeared; approving it would ask R-10 to apply a change to a superseded document. Feasible/Approve refuse with 409
`SOP_CHANGED` and the card says "The SOP has changed since this proposal was made. Generate again." Until R-10 lands
the current version never changes, so this never fires; the cost is one query in the transaction. No current SOP at
all (`null`) also counts as changed.

**Supervisor Reject ordering (§0 item 4).**
```
R-a  pre-check: readDecisionSnapshot (no transaction) → classifyDecision
        not_found → 404 · conflict → 409 · unchanged → 200 (no constraint, no redaction, no write)
R-b  createConstraint(constraintStore, deps, { claims, text: reason, now_ms,
                      source: "supervisor_rejection", source_proposal_id: proposal_id })
        → its own mask → staff-name scrub → SDP → dedupe/limit transaction → constraint doc + "constraint.created" audit
        503 (SDP down) / 409 CONSTRAINT_LIMIT / 422 (too long after redaction) → propagate; proposal untouched
R-c  transactDecision: fresh snapshot → classifyDecision again → buildDecisionWrite with
        reason = the returned constraint's (redacted) text, constraint_id = its id → proposal doc + "proposal.supervisor_rejected" audit
        a 409 here (lost race) → propagate; the constraint from R-b stays (E20)
```
- Retry after a transient failure in R-c: R-b's dedupe returns the same constraint (`duplicate: true`, normalized
  text match), R-c succeeds. Idempotent.
- If the reason's normalized text equals an existing constraint (manual or from another rejection), R-b returns that
  constraint and the rejection links to it. Correct: the rule already exists.
- The proposal's stored `reason` is the **redacted** constraint text, never the raw body text.

**Owner Reject (Q-1 = yes, Rangga 11 Oct).** The owner's reason becomes a permanent outlet constraint, exactly like
the supervisor's. The same three steps as "Supervisor Reject ordering" above, with only the source changed:
```
R-a  pre-check: readDecisionSnapshot (no transaction) → classifyDecision (actor "owner")
        not_found → 404 · conflict → 409 · unchanged → 200 (no constraint, no redaction, no write)
R-b  createConstraint(constraintStore, deps, { claims, text: reason, now_ms,
                      source: "owner_rejection", source_proposal_id: proposal_id })
        same redaction, dedupe, limit and errors as the supervisor's (503 / 409 CONSTRAINT_LIMIT / 422) → proposal untouched
R-c  transactDecision → buildDecisionWrite with reason = the returned constraint's (redacted) text,
        constraint_id = its id → proposal doc (owner_decision.constraint_id set) + "proposal.owner_rejected" audit
        a 409 here (lost race) → propagate; the constraint from R-b stays (E20 applies to the owner too)
```
- New constraint source value `"owner_rejection"` (Task 1.1b) so the stored rule says which rejection produced it;
  `created_by_role` is `"owner"` (set by `createConstraint` from the claims, unchanged).
- Owner already holds `constraints:write` (R-08 Q-11 b), so `createConstraint`'s own permission check passes; **no
  RBAC change**.
- Retry and duplicate-text behaviour are identical to the supervisor's (dedupe returns the existing constraint; the
  rejection links it).
- The owner's stored `reason` is the redacted constraint text, never the raw body text.
- There is now **one** write path for both rejections (`createConstraint`); `decideProposal` no longer calls
  `redactUserText` directly. Task 3's extraction still stands (it is `createConstraint`'s step 4), unchanged.

**Feasible / Approve.** One transaction, no pre-check (nothing to pay for before it).

**Status codes (inherited item 10; checked against `lib/auth/client/api.ts` `authedRequest`).**

| Route | Success | Client result | Errors (client result) |
|---|---|---|---|
| `GET /api/v1/proposals` | **200** | `ok` | 401 → `signed_out` (after one refresh) · 403 → `forbidden` · 409 `LIBRARY_NOT_READY` → `conflict` · 5xx → `error` |
| `POST …/{id}/review` | **200** (changed **and** unchanged) | `ok` | 400 bad JSON → `error` · 401 · 403 · 404 → `error` · 409 codes → `conflict` · 422 `invalid_body` → `invalid` · 503 → `error` |
| `POST …/{id}/approve` | **200** (changed **and** unchanged) | `ok` | same as review |

Why 200, not 201, on a reject (supervisor or owner) that also creates a constraint: the addressed resource is the proposal,
which is updated, not created; the constraint is a side effect reported through the list reload. 200 is accepted by
`authedRequest` today; **no change to `api.ts`**. A route test asserts the exact 200 for every success branch, and the
PR-B builder must re-read `authedRequest` before wiring the panel (it is the PR-B lesson from R-08).

**One list, one card, role-aware buttons.** `GET /api/v1/proposals` returns `{ open, decided }`, each item
`{ proposal: ProposalView, review, notices }`. `proposal` is exactly `toProposalView`'s output (unchanged), so the
R-08 card renders it as today. The decision buttons are a separate component under the card; which buttons show is
UI-only (mirrors the server); the server decides.

**After a decision the client re-fetches the list** (and the constraints panel after any reject). The
decision response is only `{ result, status }`. One extra GET is cheaper than building and testing a second
view-assembly path in the decision service.

**What R-09 never does:** write `sop_versions` (R-10; hard rule #9), edit or delete a constraint (R-08 E37), call
any model, change `generateProposal`'s behaviour, add a proposal status.

## 2. Global constraints (every task inherits these)

- **No device-revealing id in any response or error:** no `thread_id`, `device_id`, `question_id`, `line_id`.
  `proposal_id` and `constraint_id` are random UUIDs (already exposed by R-08). Errors use
  `NotFoundError("proposal", "proposal")`, never an id. Test-enforced with a sentinel device id in thread ids.
- **No person in any stored decision:** decisions record the role implicitly by slot (`supervisor_review`,
  `owner_decision`) and in the audit `actor_role`. No uid, email, name, staff id or device id anywhere (hard rule #7).
- **Every reason is redacted before it is stored or returned** (hard rule #3): supervisor and owner both via
  `createConstraint` (whose step 4 is `redactUserText`). Redaction failure → 503, nothing written.
- **Audit entries carry no text:** `details` holds statuses, counts and the constraint id only, never the reason.
- **Logs:** `[proposal] decided { outlet_id, proposal_id, actor, result | code }` only. Never a reason, a constraint
  text, a summary, a name or a token. A test spies on `console.*` with a reason sentinel.
- **Every Firestore read is outlet-scoped** (equality filter on `outlet_id`, or a by-id read dropped unless
  `outlet_id === claims.outlet_id`). Malformed docs skipped and logged `{ doc_id, error_class }` only.
- **Never write an explicit `undefined` to Firestore** (the bug class QA found in R-06 PR-4): build the merged
  proposal with explicit `null`s (Task 4.2) and parse it with `ProposalSchema` before `tx.set`.
- **Responses** set `Cache-Control: private, no-store`.
- **Read-only for R-09 (import, do not edit):** `lib/proposals/view.ts`, `lib/proposals/contract.ts`,
  `lib/proposals/{range,candidates,precheck,baseline,proposal-gate,prompt,wire-schema}.ts`, `lib/agents/**`,
  `config/**`, `lib/firestore/proposal-store.ts`, `lib/firestore/constraint-store.ts`,
  `app/api/v1/proposals/generate/**`, `app/api/v1/constraints/**`, `lib/auth/client/api.ts`, `lib/http/**`,
  `lib/day/**`, `lib/debrief/**`, `lib/capture/**`, `app/capture/**`, `private/**`.

  nothing else), `lib/constraints/service.ts` (Task 3.2: call the extracted helper; Task 1.1b: widen

## 3. Review focus (failure modes no single happy-path test exercises)

1. **Approval without a supervisor:** any path to `approved` that skips `awaiting_owner`, or branches on
   `requested_by_role`. Pinned: 4.T5, schema invariant 1.T4, service 5.T3.
2. **A stale proposal approved:** freshness checked only in the pre-read, not inside the transaction. Pinned: the
   check lives in `classifyDecision`, which only `transactDecision` runs for positive decisions; store test 5.S6
   asserts the threads are read with `tx.getAll`.
3. **A rejection without a constraint, or a constraint written outside `createConstraint`.** Pinned: 5.T6/5.T7
   (spy on the constraint store: exactly one `createInTransaction` per supervisor **and** per owner reject, with the
   right `source`; zero for Feasible and Approve).
4. **Unredacted reason stored** (phone number, staff name). Pinned: 5.T8 (supervisor) and 5.T9 (owner), both through
   `createConstraint`, each with a staff-name and digit sentinel and a redactor that throws.
5. **A constraint created by a reject that the pre-check would have refused** (paying SDP and writing a permanent
   rule for an already-decided proposal). Pinned: 5.T10 (pre-check conflict → constraint store never called).
6. **Device id leak** via list items or errors. Pinned: 5.T15 sentinel.
7. **A late constraint silently acknowledged.** Pinned: 4.T11, 5.T12 (ack missing one id → 409, nothing written).
8. **Explicit `undefined` in the written doc.** Pinned: store test 5.S7 (written object has no `undefined` value at
   any depth).
9. **Status line lies:** R-08's card maps every non-suppressed, non-blocked status to "Waiting for supervisor
   review". Pinned: 7.T1 (six statuses, six lines).
10. **Junk constraints from tidying** (superseded proposals rejected to clear them). Pinned: 4.T9 (superseded →
    409 for reject too), UI 7.T6 (no buttons on a superseded card).

```ts
import { MIN_EVIDENCE_DATES, MIN_EVIDENCE_FACTS } from "@/lib/proposals/constants";

/**
 * The single definition of "this cited thread is still a fact" (R-08 Task 5
 * step 8f, extracted by R-09). Used by generateProposal's commit, by the
 * decision transaction (Feasible / Approve) and by the list's stale notice,
 * so all three agree by construction. Plain code (hard rule #10).
 */
export interface FreshThread {
  status: "fact" | "open" | "unverified";
  excluded_from_evidence?: boolean;
  label_source?: string;
}

/** A missing thread (deleted, TTL-expired, foreign outlet, malformed) is not fresh. */
export function isFreshFact(t: FreshThread | undefined): boolean {
  return t !== undefined && t.status === "fact" && t.excluded_from_evidence !== true && t.label_source !== "supervisor_rejected";
}

export interface EvidenceRefLike {
  thread_id: string;
  local_date: string;
}

export function evidenceStillHolds(
  refs: readonly EvidenceRefLike[],
  fresh: ReadonlyMap<string, FreshThread>,
): { kept_threads: number; kept_dates: number; holds: boolean } {
  const kept = refs.filter((r) => isFreshFact(fresh.get(r.thread_id)));
  const kept_threads = new Set(kept.map((r) => r.thread_id)).size;
  const kept_dates = new Set(kept.map((r) => r.local_date)).size;
  return { kept_threads, kept_dates, holds: kept_threads >= MIN_EVIDENCE_FACTS && kept_dates >= MIN_EVIDENCE_DATES };
}
```
