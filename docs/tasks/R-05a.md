## Windowing details (why the shape above)
- R-04 writes **one line per segment** (`lines: [{text, start: 0, end: duration_s}]`), and segments
  are capped at 15 s with no silence ever uploaded. So within-segment gaps never matter (always
  under 90 s) — **silence is only the gap *between* consecutive segments.** Build the absolute
  timeline as `line.start_ms = Date.parse(seg.device_start) + line.start * 1000` (same for `end_ms`),
  but write `toTimedLines` to handle more than one line per segment so a future R-04 change needs no
  rework here.
- The 6-minute cap must prefer cutting at a real pause, not mid-utterance: within
  `[cap − 60s, cap]`, cut at the largest gap; on a tie take the later one; if no gap exists in that
  window, cut at the last line boundary at or before the cap. Look backward only, so live and replay
  runs agree.
- Sort by `(device_start, seg_id)`, dedupe by `seg_id`, clamp negative gaps to 0 (device clocks can
  jump). Thresholds are inclusive: a gap ≥ 90 000 ms closes the window; span ≤ 360 000 ms is the cap.
- `as_of_ms` (not `Date.now()`) tells the function which windows count as "closed" — for a full-day
  replay this is end-of-day. `window_id = w_${first seg_id}` stays stable across online and replay runs.

## Thread builder details
- `reply_to` is an index **local to one label call**, so it can never link across windows by itself —
  cross-window continuation happens only through the `thread` hint, when the model echoes an
  open-thread id from the previous window's notes. The grace period applies at that join.
- A label call's unit of input is a `LabelUnit` (possibly several batched tiny windows), not a single
  window.
- Build connected components over `reply_to` edges plus shared `thread` hints (union-find). Drop
  invalid edges (forward/self references, out-of-range, or touching a NON_WORK line) and count them.
  A component spanning different model-assigned categories sets `label_conflict: true` (the gate then
  forces a question). Lines the model never assigned go to `unassigned_line_ids` for R-05b to retry.
  A thread the model itself labels NON_WORK is dropped entirely and counted, never stored as text.
- **Grace periods** (`GRACE_MS`, grouped by why a merge is safe or unsafe — see "Open for Rangga" for
  final confirmation): incidental categories that already require supervisor confirmation regardless
  of confidence (SAFETY_INCIDENT, SECURITY_INCIDENT, DISRUPTION) share COMPLAINT's 5-minute grace,
  since a merge there can never slip through as an unreviewed fact; TRAINING keeps its spec'd 10
  minutes; everything else (ROUTINE_OPS, STAFF_CONSULT, CORRECTION, PHONE_CALL, EVENT) gets 2 minutes.
  A join is inclusive: gap from the thread's last line end to the new line start ≤ grace.

## Evidence gate details (hard rule #10)
- The gate is pure and does **no I/O**. It returns a full `GateDecision` (every check's pass/fail,
  which rule fired, threshold, confidence, evidence count, a `gate_version`). R-05b persists this on
  the thread document (R-06/R-07/R-15 all need it there) and writes one structured log line with ids
  and enums only — never free text. `audit_log` is NOT used for this (it's for human actions and
  would be flooded); the thread document plus the structured log is the complete trail.
- Precedence — every check runs and is logged; the first failure in this order fires the verdict:
  `invalid_label` (confidence NaN/out-of-[0,1], unknown category) → `label_conflict` →
  `always_question` (PHONE_CALL) → `needs_supervisor_confirm` (the 5 categories) → `no_evidence`
  (< 1 valid evidence line) → `below_threshold` (confidence < 0.9) → `passed`. Keep
  `always_question`/`needs_supervisor_confirm` as separate rules (not merged) — R-07 routes a staff
  question differently from a supervisor-confirm question.
- The 7-day expiry and "never resurrected" are the question's *lifecycle*, not the gate's one-shot
  evaluation: `expireQuestion` flips an open question past 7 days to `unverified`; `applyGateDecision`
  treats `unverified` as terminal — a later re-labelling pass (Monday's segments are reprocessed
  Tuesday, per the plan) can never turn an expired question back into a fact.
- `GateDecisionSchema` is `.strict()` with no free-text field at all — hard rules #7/#8 are enforced
  structurally here, not by convention.

## Evidence beyond the 48h segment TTL (new, confirm with Rangga)

gone long before anyone can act on it. NON_WORK text is never included. This is a new, longer-lived
retention category that doesn't exist yet in `CLAUDE.md`; flagging for explicit sign-off since it's a
real product decision, not a code detail.

## Security review (on-demand, `security-reviewer`, against the original pre-fix diff `da71808..0cb42b3`)
No secrets/injection/auth issues (pure logic, no I/O). Two findings folded into the in-flight fix
round since they land in `gate.ts`, already being touched:
- MEDIUM: `evaluateGate` never validated `category` against `CategorySchema` before using it in
  lookups — an out-of-enum category fell through every check as permissive-default and could reach
  `verdict: "fact"`, only throwing later inside `GateDecisionSchema.parse()` (an unhandled exception,
  not the graceful question-fallback hard rule #10 wants). Fix: validate first, inside `invalid_label`.
- LOW: `no_evidence` only checked `evidence_line_ids.length >= 1`, not that entries are non-empty/unique.

Two more are explicitly OUT OF SCOPE for R-05a — **tracked follow-up before R-05b's label call lands**:
- HIGH: `LabelOutputSchema.threads[].fields` (`threads.ts`) is `z.record(z.string(), z.unknown())` —
  fully unconstrained. Not exploitable yet (nothing calls the real label model), but once it does,
  any text the model puts here — including a smuggled staff name or stray base64 — passes untouched
  into `BuiltThread.fields`. Must be constrained to a bounded, structured schema (known keys, primitive
  values, max length) before R-05b ships the real label call, per hard rules #2/#3/#7.
- MEDIUM: `summary`/`runner_up.why_not` are unbounded `z.string()` with no length cap and no check
  against model-reintroduced names — R-04's redaction runs on the *input* transcript, not on text the
  label model *synthesizes*, so a hallucinated name could ride through untouched. R-05b must either run
  SDP (or the staff-name scrub from Decision 4 above) on these fields before they're accepted, and add
  a max length (~500 chars) regardless.
