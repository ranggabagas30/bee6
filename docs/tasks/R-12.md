## 0. Findings and blockers (read first)

1. **Blocked on R-10 PR-1 (PR-A start) and R-11 PR-A (PR-A merge, judge path end).** Tiffany's 5 clips are delivered
   (T-702) and live under `private/` only (audio never enters the repo, hard rule #8, or cloud storage, hard rule #2).
2. **A shared demo outlet breaks for the second judge (found by walking T-705 against the real code).** Judges arrive
   asynchronously over weeks (19 Oct – 6 Nov). On one shared outlet:
   - **The Staff step cannot work at all.** A device answers only inside its own 1-hour debrief after its last ended
     session (`lib/debrief/service.ts`: `isDebriefActive`, step 11 `not_in_debrief`), and open questions expire as
     `unverified` at that debrief end (R-07). A seeded day's debrief is long over when a judge arrives, so "Try as
     Staff (answer a debrief question)" shows no questions. Re-seeding through the real path per judge would need the
     audio stored server-side (hard rule #2) or in the repo (hard rule #8): not allowed.
   - **The proposal step is consumed.** The first judge's Feasible/Approve ships v2; every later judge sees an approved
     proposal, then `SOP_CHANGED` on anything older (R-09), and junk rejection text becomes permanent constraints
     (R-09 §0 item 8).
   - **The review step is consumed** after the first fast-forward (R-11 `NOTHING_TO_REVIEW`).
3. **Decision (default, §11 Q-1): one sandbox outlet per judge visit, cloned from a template outlet that was seeded
   through the real segment API.** The template (`demo-tpl-outlet`) is produced once by Rangga's machine sending
   Tiffany's clips through the deployed `/api/v1/segments` route; the real tick, labeller, gate and question writer
   produce its threads and questions (T-703 holds for every output). "Try as …" clones the template's pipeline output
   into a fresh outlet `sbx-<hex>` with a fresh judge device, **re-arms** the last day's debrief so it is open for
   1 hour from now (the only state change the clone makes, stated honestly in the README, §11 Q-2), and signs the judge
   in to that sandbox. Every role switch stays in the same sandbox, so the story is continuous and private. Judges never
   collide; junk constraints and approvals die with the sandbox.
4. **No rate limit or token ceiling exists in code today.** `DAILY_TOKEN_CEILING` (CLAUDE.md §6/§7) is not read
   anywhere; the per-device answer rate limit was deferred (`lib/debrief/constants.ts`). R-12 builds **demo caps only**
   (sandboxes per IP per day, sandboxes per day, generations per sandbox and per day). The general per-outlet token
   ceiling stays a known gap for the pilot (§11 Q-7).
5. **2-hour sessions need a server-side expiry.** Firebase ID tokens refresh indefinitely. R-12 adds an optional
   `demo_exp_ms` claim (custom token developer claim) checked in `requireClaims`, and an optional `expires_at_ms` on
   judge device docs checked in device auth. Both are additive; real accounts and the real shop phone carry neither and
   behave exactly as today. This touches the auth core: security-reviewer mandatory.
6. **R-11's daily review run reads "all outlets" with a cap of 50.** Sandboxes are outlets, so R-11 must skip them and
   read more. R-12 Task 9 is a two-line change to R-11's code (and `R-11.md` §8 carries the note). R-12 also deletes
   expired sandboxes lazily (Task 5) so their number stays small.
7. **Fast-forward's "after" window is empty in a sandbox** (template days are in the past, v2 is in force from
   tomorrow), so the review card shows "no suggestion: fewer than 2 captured days" (R-11 §0 item 6). Honest, but flat.
   Default: accept it (humans still pick a verdict, the outcome is still stored). Option: a time-shifted template
   (§11 Q-8, +1 h).
8. **T-708 "refusal for inputs that try to change instructions"** is already met by R-08: constraint text and
   summaries enter the prompt marked as data, the per-call strict output schema limits what the model can return, and
   two humans approve. No new code (security-reviewer confirmed for R-08 PR-C).
9. **Effort: 8.4 h** against the backlog's 4 h (**+4.4 h**). The shared-outlet alternative is ≈ 4.5 h but fails T-705
   for the second judge (§11 Q-1). Why, and the cut list, in §9.

## 1. Architecture (decisions and why)

**Three moving parts.**
1. **Template (once, offline from Rangga's machine, real path).** `scripts/demo-seed-template.ts` acts as a phone: it
   pairs the template device through `/api/v1/devices/pair`, opens backdated sessions through the real session routes,
   `PUT`s each clip to the real `/api/v1/segments/{device}:{seg}` route on the deployed demo service, and ends each
   session. The deployed tick (every 2 min) labels and gates it. Result: `demo-tpl-outlet` with 3 business days of
   threads, questions and capture sessions, plus the fictional SOP v1 from the seed. The script never writes Firestore
   (it only polls read-only to report progress).
2. **Sandbox per visit (on "Try as …").** `POST /api/v1/demo/session` (anonymous, demo only):
   - first call (no `sandbox_key`): rate-limit, create `sbx-<12 hex>` by cloning the template (pure id rewrite +
     re-arm, batched writes), return a `sandbox_key` (random, returned once, stored as SHA-256) and credentials for the
     requested role;
   - later calls (`sandbox_key` given): find the sandbox by key hash, refuse if expired, return credentials for the
     new role. No new clone.
   - Owner/supervisor credentials: a Firebase **custom token** with claims `{ outlet_id: sbx, role, demo_exp_ms }` for
     uid `demo-<role>-<sbx>` (DEV-05 §3 design). The browser calls `signInWithCustomToken`; from there on it is the
     normal ID-token path, unchanged RBAC.
   - Staff credentials: the sandbox's judge device id and a fresh device token (hash on the device doc, `expires_at_ms`
     = sandbox expiry). The browser writes them to the same `localStorage` keys `/pair` writes (`bee6.device_token`,
     `bee6.device_id`) and opens `/capture`, which then shows the re-armed debrief.
3. **Demo bar (every page, demo only).** A thin bar under the top bar: "Demo · you are: Staff / Supervisor / Owner ·
   Switch to …" and "Session ends at HH:MM", plus a "Simulated time" chip on `/reviews`. Switching calls the session
   route with the stored key.

**Why clone and not re-run.** Re-running the pipeline per judge needs the audio (forbidden server-side) and takes
minutes (tick cadence + model latency) against a 4-minute path. Cloning copies outputs the real pipeline already made;
only ids, the outlet, the device and the last debrief's timing change.

**Cloning rules (pure, `lib/demo/clone.ts`).**
- **Source set** (template outlet only, all read with `outlet_id == "demo-tpl-outlet"`): `outlets` doc, `staff`,
  the template `devices` doc, `capture_sessions`, `threads`, `questions`, `sop_versions` (v1 only). **Not cloned:**
  `segments` (48 h TTL, not read by any judge screen: the day record reads thread lines), `label_units`,
  `pipeline_locks`, `corrections`, `constraints`, `proposals`, `proposal_locks`, `reviews`, `outcomes`, `audit_log`,
  heartbeats, `users`.
- **Id rewrite:** the template ids are chosen to be unique tokens: outlet `demo-tpl-outlet`, device `demo-tpl-phone`
  (neither is a substring of the other). The clone replaces every occurrence of `demo-tpl-phone` with the judge device
  id `jdg-<12 hex>` and then every occurrence of `demo-tpl-outlet` with `sbx-<12 hex>`, in **every doc id and every
  string value at any depth** (thread ids embed the device id, question ids embed thread ids, session doc ids embed the
  device id, staff/device/SOP doc ids embed the outlet id). Session `session_id` uuids are kept (the doc id already
  differs by device). Text fields (summaries, line text) never contain these tokens; a test asserts the template has no
  such token in any free-text field (it would be a template bug).
- **Re-arm the last debrief (the only state change):** let `D` = the template device's `last_ended.business_date` and
  `S` = its session for `D`. In the clone: `S.ended_at_ms = now_ms`, `S.debrief_ends_at_ms = now_ms +
  DEBRIEF_DURATION_MS`, `S.end_reason = "selesai"`; device `last_ended = { business_date: D, end_reason: "selesai",
  ended_at_ms: now_ms, debrief_ends_at_ms: now_ms + DEBRIEF_DURATION_MS }`. Every question of that device created for
  `D`'s debrief (the ones the template's debrief end expired) gets `status: "open"`, `expired_by_debrief_end_ms:
  null`, no answer fields; the thread state those questions belong to is restored exactly as the expiry changed it
  (the exact fields are fixed by the Task 0 spike from `lib/pipeline/gate.ts` and R-07's expiry writer; the plan's
  default is below in Task 4.2 and must be confirmed before coding).
- **Sandbox outlet doc:** the template outlet doc with the new id and a new optional `sandbox` object
  `{ template_outlet_id, created_at_ms, expires_at_ms, key_sha256 }`; `project_kind` stays `"demo"`; `name` "Demo
  Bakehouse".
- **Judge device doc:** `token_hash` = bcrypt of a new token, `paired_at` = now, `revoked: false`, pairing fields
  `null`, `label` "Demo shop phone", new optional `expires_at_ms` = sandbox expiry.
- **Size bound:** the template must stay under `TEMPLATE_DOC_MAX = 400` docs (checked at clone time; over → 503
  `template_too_large`, logged). Written in batches of ≤ 400 writes.

**Sessions expire after 2 h.** `SANDBOX_TTL_MS = 2 h` from creation (not from the last switch). After that:
owner/supervisor tokens → 401 `demo_session_expired` from `requireClaims`; the judge device → 401 from device auth;
the session route refuses the old key (410-like 409 `SANDBOX_EXPIRED`), and the landing offers "Start again" (a new
sandbox).

**Rate limits and caps (plain code, Firestore counters).**

| Limit | Value (default, §11 Q-3) | Where | Over the limit |
|---|---|---|---|
| New sandboxes per IP per UTC day | 10 | `POST /api/v1/demo/session` without key | 429 `rate_limited`, `retryAfterSeconds` to next UTC midnight |
| New sandboxes per day (all IPs) | 300 | same | 429 `demo_daily_cap` |
| Role switches per sandbox | 30 | same, with key | 429 `rate_limited` |
| Proposal generations per sandbox | 5 | `POST /api/v1/proposals/generate` when `outlet.sandbox` is set | 429 `demo_generate_cap` |
| Proposal generations per day (all sandboxes) | 300 | same | 429 `demo_daily_cap` |

- IPs are never stored: the key is `SHA-256(ip + ":" + utc_date + ":" + DEMO_IP_SALT)` (`DEMO_IP_SALT` from Secret
  Manager). The client IP is the **first** entry of `x-forwarded-for` (Cloud Run's front end sets it); missing → the
  literal `"unknown"` bucket (shared, so it is limited too).
- Counters: `demo_counters/{key}` docs `{ kind, count, day, expires_at }` incremented in a transaction; `expires_at`
  (native Timestamp, +2 days) gets a Firestore TTL policy (dev-ops).
- The **project quota cap** (T-708) is a Vertex AI quota set in the console by dev-ops on `bee6-playground`.

**Demo mode gate.** Every R-12 server path first checks `process.env.DEMO_MODE === "true"`; otherwise 404. The
template outlet must have `project_kind === "demo"`; the sandbox inherits it. The pilot project never sets
`DEMO_MODE`, so none of this is reachable there (the same double guard R-11 uses for fast-forward).

**What R-12 never does:** store or replay audio server-side; write Firestore from the template script; hand-write a
label, summary, question, proposal or outcome; change RBAC permissions; give a judge any route a real role lacks; touch
the pilot project.

## 2. Global constraints (every task inherits these)

- **Demo only:** every new route and every new branch in shared code is inert unless `DEMO_MODE === "true"` and the
  outlet is `project_kind: "demo"` with a `sandbox` object (shared-code branches key off the claim/doc field, which
  real principals never have).
- **No person data:** the template uses only fictional staff ("Ari Demo", "Bella Demo") and fictional clips; staff docs
  are cloned (needed for the name scrub) and stay in `staff` only. Custom-token uids are `demo-<role>-<sbx>`; no email.
  No raw IP stored anywhere (hashed with a secret salt, per day).
- **Audio:** stays on Rangga's machine and in the in-memory segment request (hard rule #2). The script reads clips
  from `private/demo-clips/` (gitignored) and never logs bytes or base64.

  no key.

  SHA-256; device tokens only as bcrypt.
- **Responses** set `Cache-Control: private, no-store`.
- **Read-only for R-12 (import, do not edit):** `lib/proposals/**` (except the cap check in Task 7, which lives in the
  route), `lib/sop/**`, `lib/reviews/**` (except Task 9), `lib/debrief/**`, `lib/pipeline/**`, `lib/capture/**`,
