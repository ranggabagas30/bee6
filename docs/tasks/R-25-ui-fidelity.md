**Sequencing rules for shared files**
1. `app/ui/**` and `app/globals.css`: only G0. Another group that needs a primitive change (new variant, token, class) files it to the PM as "G0 request: <file>, <exact change>"; G0 ships it as a follow-up sub-PR; the requester rebases. No group adds page-specific CSS to `globals.css`; page CSS goes in that page's `*.module.css`.
2. i18n: every slice file has exactly one owner (table above). A group needing a key in another group's slice **adds it to its own slice** (keys are global across slices; `v2.test.ts` enforces uniqueness and EN/ID parity). No key renames, no deletions in R-25 (unused keys are harmless; renames churn tests). New keys: `C-<area>-...`, EN final from the board, ID marked `// PROVISIONAL` unless taken from the UX-03 copy sheet.
3. `lib/i18n/dict.ts`: only G1a (base keys). Nobody else edits it (slices reach `DictKey` without touching it).
4. Tests live with their component and belong to the group that owns the component; `lib/i18n/*.test.ts` and `app/*/import-boundaries.test.ts` are edited only by the owner of the file they pin, and never loosened (an import-boundary failure means the change is wrong, not the test).
5. Merge order into `feature/r-25`: G0 → then by readiness. A merge conflict goes back to the sub-branch's developer (rebase onto `feature/r-25`), never resolved by the PM.

**Branching (same pattern as R-24).** Integration branch `feature/r-25` off `origin/develop` `eac54ff`, in its own worktree (`../bee6-r25`). Each group works in its own worktree on `feature/r-25-<group>` (e.g. `feature/r-25-g1a`) off `feature/r-25`, opens a PR **into `feature/r-25`** (pre-push hook: lint, build, vitest), gets a tech-lead gate (review template in `.claude/agents/tech-lead.md`), is merged by the PM. One final PR `feature/r-25` → `develop` (tech-lead full review, QA on `web-develop`), then the single release PR `develop` → `main` (R-24 flag-off + R-25). Nobody runs a mutating git command in the main checkout.

## 4. Severity rubric and cut line

- **P0** — wrong behaviour, or a missing/incorrect element or copy that a judge sees and that breaks the story (wrong button label or state, missing guide card content, missing stage, wrong screen after an action, a board element with no counterpart, a date/clock shown where the board hides it or vice versa).
- **P1** — layout, spacing, component choice, order, state or copy differences clearly visible on a phone at arm's length (wrong primitive e.g. pill vs chip, wrong order of blocks, a 2-line vs 1-line wording, a missing sub line, wrong tone colour, wrong date/clock **format or placement**).
- **P2** — small px/shade differences, illustrative board dates (real dates are correct), micro-copy punctuation.
- Dates: real business dates and the real `review_date` are **correct by definition**; their format (`dayLabel`/`shortDate`/`clockLabel`) and placement are P1 if wrong.
- Conflict rule: §0 of this doc (board > UX-03 on look/wording; tech spec on behaviour). A "gap" that would change behaviour (a gate, a route, a guard) is **not a UI gap**: it goes to Rangga as a question, not to a uiux developer.
- Cut line: **P0 + P1 today** on the release PR. **P2 only if it rides a sub-PR already open before the 15:00 hard stop**; a separate P2 batch after the release needs Rangga's explicit yes (§10 Q2).
