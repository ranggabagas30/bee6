## 1. Architecture (decisions and why)

**Auth: Firebase Authentication email + password, Bearer ID token, no session cookie.** The browser signs in with
`signInWithEmailAndPassword`, posts the ID token once to the existing `POST /api/v1/auth/session` (links the
`users` doc and sets claims), force-refreshes the token to pick up the claims, then sends
`Authorization: Bearer <ID token>` on every API call. Server path unchanged from R-02 (`requireClaims` →
`verifyIdToken` → `CustomClaimsSchema` → `authorize`).
- **Why Firebase email/password and not a home-made username table:** same Firebase ID token, same
  `requireClaims`, same claims; the password hashing, rate limiting (`auth/too-many-requests`), token refresh and
  revocation are Firebase's. A home-made scheme would need its own hashing, lockout, session tokens and a second
  guard. It stays inside CLAUDE.md §3's auth system (Firebase Auth) and hard rule #1 (Google only); only the
  sign-in *method* changes.
- **Why it is safe with the public web API key:** anyone can call Firebase's sign-up REST endpoint with the public
  key and create an email/password account, but such an account has `email_verified: false`, and
  `linkGoogleUser` refuses unverified emails, so it never gets claims and every API call is 401. Only accounts
  created by Task 9's admin script (`emailVerified: true`) can link. If someone pre-registers a seeded email before
  the script runs, the script refuses unless `--reset-password` is given, which then replaces the password and
  revokes the squatter's refresh tokens (Task 9). Disabling self sign-up entirely needs the Identity Platform
  upgrade; optional defence in depth, not required (§9).
- **"Username":** Firebase needs an email-shaped identifier. It does not have to receive mail (the script marks it
  verified, and no flow sends mail), so Rangga may use real addresses or username-like ones (e.g.
  `supervisor@proofed.invalid`). The field is labelled "Email".
- Only `firebase/app` and `firebase/auth` are ever imported in browser code. An import-ban test forbids
  `firebase/firestore`, `firebase/database`, `firebase/storage` anywhere (hard rule #6).

**Firebase web config at runtime, not build time.** One image for pilot and demo (`cloudbuild.yaml`). The server
page reads `FIREBASE_API_KEY`, `FIREBASE_AUTH_DOMAIN`, `FIREBASE_PROJECT_ID`, `FIREBASE_APP_ID` from `process.env`
after `await connection()` (Next 16 runtime-env pattern,
`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md` L207-221) and passes them as a prop.
Public identifiers by design, not secrets; already named in `.env.example`.

**One read route, role-shaped response; the boundary is the server.** `GET /api/v1/day/{date}`. The server decides
the view: `can(role, "day:read:evidence")` → supervisor shape, else owner shape (zod discriminated union on
`view`). **The owner shape holds confirmed facts only** (Rangga, 9 Oct): its `display_status` enum has only the
three fact values, it has no `question_count`, no field that can hold a quoted line, reason or handle, and the owner
path **never reads** thread `lines`, any `questions` doc or any `corrections` doc.

**One write route, through the gate.** `POST /api/v1/threads/{id}/confirm` (supervisor, `labels:confirm`; the
`{id}` path segment carries the opaque handle, never a raw thread id; segment named `id` to match the web spec row
and `/api/v1/questions/{id}/answer`).
Body `confirm` or `override` + category. The service decrypts the handle, and inside one Firestore transaction
re-reads the thread and its question, checks eligibility, runs `evaluateGate({ ..., supervisor_decision })`, and
writes the thread patch + one `audit_log` entry (role only) only if the gate passes. Nothing else writes facts.
**v4:** the same route takes a third body action, `reject` (Task 15). Why one route and not
`POST /api/v1/threads/{id}/reject`: reject has the same permission (`labels:confirm`), the same handle, the same
eligibility rule, the same transaction (re-read thread + question), the same audit shape and the same error set;
a second route would copy the guard, handle decryption, transaction and error mapping for one extra branch, and
give two places to keep in sync. The body is already a discriminated union on `action`, so reject is one more arm.
The cost is a path name that says "confirm" for a reject; the web spec §6.2 row is updated to say the route takes
`confirm | override | reject` (PM doc update, §12). A reject also goes through `evaluateGate` (verdict always
`question`), so the gate stays the only code that decides fact vs not-a-fact.

**One screen component, not two.** `DayRecordView` renders the union; `ThreadCard` renders evidence, the staff
answer and the supervisor actions only when the row type has them (TypeScript narrowing on `view`). The security
boundary is the response shape, not the component split.

**Pure logic, thin store, thin route** (repo convention): `lib/day/attribution.ts`, `day-status.ts`, `derive.ts`,
`thread-handle.ts` (pure) → `lib/day/service.ts`, `lib/day/confirm-service.ts` over injected stores →
`lib/firestore/day-store.ts` → `app/api/v1/day/[date]/route.ts`, `app/api/v1/threads/[id]/confirm/route.ts`.

**v3 additions (Tasks 11-14).**
- **Runner-up** is one more supervisor-only field on the existing supervisor row (`runner_up`), read with the
  supervisor's field mask, shown in a native `<details>` inside the supervisor `ThreadCard`. No new route.
- **Unlabelled rows** are a second, supervisor-only array (`unlabelled`) on the existing day response, not a new
  variant of the thread row: the thread row stays exactly as PR-2 ships it, and each unlabelled row carries
  `after_row` (the `row` of the last thread that started at or before it) so the client interleaves them by time
  without a shared counter. This keeps PR-6 purely additive.
- **Questions queue** is the supervisor branch of the existing `GET /api/v1/questions` (web spec §6.2), selected
  by the **absence** of `X-Device-Id`; the device branch is moved into a function verbatim and behaves identically.
  Queue items reuse the supervisor row mapper and `ThreadCard` + `ThreadActions` (PR-5), plus a `date`. So the
  queue is "every answered thread still waiting for a supervisor, across the last 14 days" with the same
  confirm/override buttons, not a second action surface.
- **Owner home** is `GET /api/v1/home` (owner only, new permission `home:read`), built on `getDayRecord`'s owner
  path (`param: "today"`), so it inherits the facts-only boundary for free. **It is the owner's start page after
  sign-in** (Rangga, v4 Q-G); supervisors start on `/day`. Its other tiles are added by the tasks that create their
  data (Task 14b with R-09, 14c with R-11), each as a strict-schema extension, never a guessed shape. No cost tile
  (v4 Q-F: next MVP).

**Performance shape.** One range query on `threads` for the day (field-masked), one small `capture_sessions`
query, one `devices` query, then (supervisor only) `getAll` batches for questions and corrections, all
field-masked. Owner: no question/correction reads at all. Hard cap 1000 threads with a `truncated` flag. Category
filtering is client-side; the language toggle switches copy only (no refetch). Detail in §7.

## 2. Global constraints (every task inherits these)

- **No identifiers that reveal a device in any day-record or confirm response:** no `thread_id`, `question_id`,
  `device_id`, `answered_device_id`, `unit_id`, `line_id`, `session_id`. Rows carry `row` (0-based position);
  supervisor rows also carry the encrypted `handle`. Test-enforced. Error messages too: a missing thread is
  `new NotFoundError("thread", "handle")` (the literal word), **never** the thread id (`NotFoundError` puts its
  second argument in the response message).
- **Owner response = confirmed facts only:** rows whose `status === "fact"` and `excluded_from_evidence !== true`.
  No `evidence`, `staff_answer`, `handle`, `can_review`, reason, line text or `question_count`. The owner path never
  reads `threads.lines`, `threads.evidence_line_ids`, any `questions` doc or any `corrections` doc. Test-enforced at
  schema, service, store and render level.
- **Never translated:** `summary`, evidence line text and the staff reason are shown exactly as stored in both
  languages. The toggle switches chrome, category labels, status labels, dates and counts only.
- **No model call anywhere in R-06** (hard rules #1, #4, #5 trivially satisfied). R-06 product code writes **only**
  in Task 10 and (v4) Task 15 (thread label fields + one audit entry; no free text). The fixture script (Task 8) writes fictional
  data to the demo project only; the provisioning script (Task 9) writes only Firebase Auth accounts.
- **Every Firestore read is outlet-scoped:** queries filter `outlet_id == claims.outlet_id`; every doc fetched by id
  is dropped (read) or 404 (write) unless its `outlet_id === claims.outlet_id`.
- **Logs:** malformed or foreign docs are logged as `{ doc_id, error_class }` only (the `logSkippedDoc` pattern in
  `lib/firestore/tick-store.ts`). Never a line, summary, reason, token, password or handle key.
- **API responses** set `Cache-Control: private, no-store`.
- 360 px first; touch targets ≥ 48 px; no horizontal scroll. Copy only through `t(lang, key)`.
- **Read-only for R-06** (DEV-03 is changing some in parallel): `lib/capture/calendar.ts`, `lib/capture/contract.ts`,
  `lib/capture/dev-mode.ts`, `next.config.ts`, `app/capture/**`, `lib/debrief/**`. Import, do not edit. If you

## 3. Review focus (failure modes no single happy-path test exercises)

1. **A non-fact row, quoted line or reason reaching the owner** via a shared mapper, a spread of the stored doc, or a
   client branch. Pinned: Task 3 (owner schema rejects extra keys and non-fact statuses), Task 5 (sentinel strings
   absent from the owner JSON, including the summary of every non-fact row; store never asked for `lines`,
   questions or corrections), Task 7 (owner render has no `blockquote`, no sentinel, no action button).
2. **A device id leaking** through `thread_id` / `question_id` / an error message / the handle. Pinned: Task 5 and
   Task 10 (JSON of every response contains no fixture device id; the handle round-trips and is not the id).
3. **The closing hour on the wrong day** (lines 01:00-02:00 of D+1 inside D's session). Pinned: Task 2 grid.
4. **500 instead of 401** on an expired token. Pinned: Task 1.
5. **A discarded session's threads shown** before Cancel-B deletes them. Pinned: Task 2 and Task 5.
6. **The shop-phone bundle growing** because `/capture` imports the Firebase SDK. Pinned: Task 4 import-ban test.
7. **A supervisor decision silently undone** by the next tick continuing the thread. Pinned: Task 10 tick-store test.
8. **A fact written outside the gate**, or a supervisor confirm that ignores `no_evidence`. Pinned: Task 10 gate
   tests (v3 path) and confirm-service test (gate blocked → nothing written).
9. **A password or ID token logged.** Pinned: Task 4 (no `console.*` call receives them; tests spy on console).
10. **The debrief broken at go-live by the queue branch** (Task 13 edits R-07's device route). Pinned: Task 13 (the
    device branch body is moved verbatim; every existing device test still passes with only the header added;
    a request with `X-Device-Id` never reaches `requireClaims`).
11. **An `unlabelled_unit` question id (device id inside) or a `runner_up` reaching a response or the owner.**
    Pinned: Task 11 and Task 12 sentinel tests; owner schema rejects both keys.

**13.4 Service (`lib/day/queue-service.ts`):**
```ts
export const QUEUE_LOOKBACK_DAYS = 14;
export const QUEUE_SCAN_LIMIT = 500;
export async function getReviewQueue(
  store: Pick<DayStore, "getOutlet" | "listAnsweredGateQuestions" | "getThreads" | "getCorrections">,
  input: { claims: CustomClaims; now_ms: number; handleKey: Buffer | null },
): Promise<ReviewQueueResponse>;
```
In order:
1. `assertPermission(claims, "questions:read")` then `assertPermission(claims, "day:read:evidence")` (supervisor
   only: the owner lacks the first, staff the second, device both) — before any store call.
2. `outlet = await store.getOutlet()`; `null` → `NotFoundError("outlet", claims.outlet_id)`; `assertOutlet`.
3. `qs = await store.listAnsweredGateQuestions(now_ms - QUEUE_LOOKBACK_DAYS * 86_400_000, QUEUE_SCAN_LIMIT + 1)`;
   `scanTruncated = qs.length > QUEUE_SCAN_LIMIT`; keep the first `QUEUE_SCAN_LIMIT`; drop any with a foreign
   `outlet_id`; dedupe by `thread_id` (keep the newest answer).
4. In parallel: `threads = getThreads(unique thread ids)`, `corrections = getCorrections(question ids)`.
5. Keep a question iff its thread exists, `thread.outlet_id === claims.outlet_id`, `thread.status === "open"`,
   `thread.label_source !== "supervisor_confirmed"`, (v4) `thread.label_source !== "supervisor_rejected"`, and
   `effective = thread.confirmed_category ?? thread.category` is not `NON_WORK`. (PR-7 merges after PR-5, so
   `"supervisor_rejected"` is already in `ThreadSchema` and `DayThreadRow`.)
6. `date = correction?.debrief_business_date ?? businessDateOf(thread.first_line_start_ms, outlet.timezone)`.
7. Sort by `date` descending, then `first_line_start_ms` ascending, then `thread_id` (ordering only). Cap at
   `QUEUE_CAP`; `truncated = scanTruncated || kept.length > QUEUE_CAP`.
8. Map: `{ ...toSupervisorThread(thread, { index, tz, outletId, handleKey, question: { outlet_id, question_id,
   status: "answered", answer }, correction }), date }` (build the `question` object explicitly from the queue row;
   never spread a stored doc; spreading the mapper's own output is fine).
9. `return ReviewQueueResponseSchema.parse({ view: "supervisor_queue", items, truncated })`; a parse failure throws
   (500).

Known limit (state in the PR): the queue does not re-check session attribution (no discarded-session filter): a
discarded session has no debrief, so its questions cannot be answered, and Cancel-B deletes them.

**The product rule this task encodes (Rangga, v4 Q-C: approved).** A supervisor who reads the evidence and the
staff answer and decides "this did not happen as labelled" can reject the note. A rejected note:
- is **never a fact** (not on the owner view, not counted in `fact_count`, not evidence for R-08, which reads

  undo; no separate undo button);
- is recorded once in `audit_log` with `actor_role: "supervisor"` only.

`unverified`). That includes facts: a supervisor may reject a model fact that has an answered question, a
staff-confirmed fact or a supervisor-confirmed fact (a mistaken earlier confirm). A model fact **without** a
question is not reviewable (Q-B, unchanged), so it cannot be rejected either. Reject on a `rejected_by_staff` row
is allowed: the supervisor agrees with the staff, and the row leaves the queue.

## 7. Performance: what "a 14-hour day loads in < 2 s on a phone" requires

- **Volume.** Windows are ≤ 6 min (`lib/pipeline/windowing.ts` cap 360 000 ms), so a 14 h day is ≤ 140 windows
  per device; at 1-3 threads per window with silence removed, a busy device lands at ~100-300 threads. Plan for
  400 per device-day, cap 1000 per outlet-day. No real pilot day exists yet, so the check uses Task 8's fixture.
- **Reads per load:** 1 outlet + ≤ 3-day sessions + N threads + devices; supervisor also ⌈q/100⌉ question batches
  and the correction batches. All field-masked; the owner never downloads line text and reads no question or
  correction. Expected server time on a warm instance in `asia-southeast2`: ~0.3-0.6 s for 400 threads. Handle
  encryption: 400 AES-GCM seals ≈ 1-2 ms.
- **Payload (revised, tech-lead PR-2 review, 10 Oct — real per-field JSON overhead measured higher than the
  original estimate):** owner stays ≤ 150 KB throughout. Supervisor budget rises by stage, using the fixture
  sizes fixed in Task 5 (§5, L974-977 — don't let these shrink again per PR): **< 400 000 bytes (PR-2, this
  PR, no runner-up/handle yet)** → **< 500 000 bytes (from PR-3, Task 11's runner-up field added)** →
  **< 560 000 bytes (from PR-5 on, the confirm/override handle + `can_review` add another ~40-45 KB)**.
  Task 12's unlabelled rows are small (≤ 200 × ~150 bytes) and don't move this further. The queue (Task 13)
  is ≤ 200 items, and the home (Task 14a) reuses the owner read, which never downloads line text. The 2 s
  load target is measured live (deployed, gzip applies), not against this uncompressed JSON-size proxy.
- **Client:** the Firebase auth SDK loads only on `/sign-in` and `/day` (import-ban test keeps it off `/capture`).
  400 cards render without virtualisation; `content-visibility: auto` keeps paint cheap. Filtering is in memory.
- **No pagination, no new cache.** One composite index (§9).
- **Cold start: decided (Rangga, 9 Oct) — the 2 s must also hold cold.** That is `--min-instances=1` on the
  `web` Cloud Run service, a running cost, done by **dev-ops as a follow-up** (§9), not a build task and not in
  the effort total. QA measures both warm and (after dev-ops' change) the first request after an idle period.
  **v4:** with the pilot postponed, the service judges hit is the **demo** `web`; the 9 Oct decision was made for
  the pilot, so applying it to the demo is §12 Q-D (Rangga confirms the running cost).
- **v4, where the 2 s is measured:** only on a deployed Cloud Run service. `develop` is not deployed, so the
  measurement happens on the `develop` preview service if dev-ops creates it (§12 Q-H), else on the demo after
  promotion #1 (§10). A local `next start` run is a smoke check, not the acceptance measurement.
