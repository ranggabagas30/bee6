## 0. Findings and blockers (read first)

1. **No blocker for PR-1. PR-2 is blocked on R-09 PR-A merging** (it extends `decideProposal`, `DecisionSnapshot`
   and `transactDecision`, which do not exist on `develop` yet).
2. **The "pipeline" does not read the SOP anywhere except proposal generation (found in the code).** `git grep -i sop`
   over `lib/pipeline`, `lib/debrief`, `lib/day`, `app/api/internal` and `lib/agents` finds no SOP read: windowing,
   threads, labels, the gate and debrief questions never see SOP steps (questions are role-agnostic, technical spec
   §3.1 step 5). The only SOP consumers are:
   - `generateProposal` (`lib/proposals/service.ts` step 5): `store.getCurrentSop()` = the **highest-version** doc of
     the outlet (`lib/firestore/proposal-store.ts` `getCurrentSop`, `where outlet_id == X, limit 50`, max `version`).
     Its steps go into the prompt (`lib/proposals/prompt.ts`: `SOP v${version}` + one line per step) and its id into
     `generator.sop_version_id`.
   - `toProposalView` (step titles for the card).
   - R-09 (planned): `getCurrentSopVersionId` for the `SOP_CHANGED` guard (same "highest version" query).
   - R-11 (not planned yet): the metric "before" window (under v1) and "after" window (from v2's ship date).
   So "the pipeline reads v2 from the next morning" has to be made concrete. §1 "Latest vs in force" decides it.
3. **"v2 = v1 + the approved change" is undefined in the data (found in the code).** A proposal stores
   `target_step_id` (an existing step id, or `null` for a new step), `change_title` (stored ≤ 160) and `change_text`
   (stored ≤ 800). Nothing says whether `change_text` is the **new text of the step** or a **description of the
   change** ("Add a failure path for…"), and the ProposalAgent's prompt does not tell the model either (rules 1-10 in
   `lib/proposals/prompt.ts` `SYSTEM_INSTRUCTION`). For `add_failure_path` a description would wipe the original step
   text if applied as a replacement. Decision (§1 "Applying the change", §11 Q-1): **`change_text` is the full new step
   text**, made explicit by one new prompt rule (Task 2, a small edit to merged R-08 code).
4. **`SopStepSchema` caps are smaller than the proposal's stored caps (found in the code).** `title ≤ 80`,
   `text ≤ 600` vs `change_title ≤ 160`, `change_text ≤ 800` (stored caps are 2× wire caps because redaction tokens grow
   text). Building a v2 step from proposal text could fail the parse. Fix: widen `SopStepSchema` to `title ≤ 160`,
   `text ≤ 800` (Task 1). Widening is back-compatible: every existing v1 doc still parses. **Never truncate.**
5. **A new step has no role and no position in the proposal.** `SopStepSchema.role` is required. Default (§11 Q-2):
   role `"staff"`, appended at the end, `step_id = "p-" + the proposal id without hyphens`, title = `change_title`.
6. **`SopVersionSchema` has nowhere to put the change, the effective date or the review date.** R-08 defined only
   `steps`, `source`, `source_proposal_id`, `created_at_ms`. R-10 adds three **optional** keys (`previous_version_id`,
   `effective_from_date`, `change`) plus invariants (Task 1). Additive: the seeded v1 docs on both projects lack the
   keys and still parse. R-08 §0 item 4 said R-10 "extends" this contract; this is that extension, not a redesign.
7. **Review date (R-08 Q-7 / R-09 E28), decided here: counted from the ship date** (§1 "Review date", §11 Q-3).
   Today `content.review_date = generation date + review_after_days`. If the owner approves days after generation,
   the "after" window R-11 measures shrinks, possibly to zero. R-10 recomputes it at approval as
   `effective_from_date + review_after_days` and writes it on both the SOP version and the proposal.
8. **The done-when's "Wed 21 Oct" cannot be met literally and is now moot.** The pilot go-live is postponed with no
   date (`docs/HANDOFF.md`, 9 Oct); submission is **18 Oct on the demo project**. With the minimum 7 review days and a
   next-morning effective date, an approval on Thu 15 gives a review on Fri 23, not Wed 21. Proposed restatement
   (§11 Q-5): "on the demo outlet, SOP v2 exists with a review date after 18 Oct; generation reads v2 from the moment
   it ships; v2 is in force from the next outlet-local morning."
9. **No SOP read route or screen exists.** Web spec §6.2 lists `GET /api/v1/sop` and `GET /api/v1/sop/diff`; neither
   is built, and no page shows the SOP. The plain before/after list therefore needs one route and one page (PR-1). The
   diff route stays unbuilt (cut #51); the list replaces it.
10. **Effort: 4.8 h** against the backlog's 1 h (**+3.8 h**). Why, and the cut list, in §9.

## 1. Architecture (decisions and why)

**Same split as R-08/R-09: pure planner, thin service, thin store, thin route.**
- `lib/sop/ship.ts`: pure `planShip` (applies an approved proposal to the current SOP and returns the new version, or a
  conflict), `effectiveFromDate`, `shipReviewDate`, `newStepId`. No I/O.
- `lib/sop/in-force.ts`: pure `latestSop` and `sopInForce` (which version applies on a given outlet-local date).
- `lib/sop/contract.ts`, `lib/sop/service.ts`, `lib/firestore/sop-store.ts`, `app/api/v1/sop/route.ts`: the read side.
- `app/sop/*`: the page with the plain before/after list.
- PR-2 wires `planShip` into R-09's owner-approval transaction. No new write route, ever.

**Latest vs in force (this is what "the pipeline reads v2 from the next morning" means in code).** Two notions, both
plain code:
- **Latest** = the highest-version doc of the outlet. It changes **at approval**. Used by: proposal generation
  (`getCurrentSop`, unchanged), R-09's `SOP_CHANGED` guard (unchanged), and `planShip` (v{n+1} is built on it).
- **In force on date D** = the highest version whose `effective_from_date` is `≤ D` (a seed version with no
  `effective_from_date` is in force from the start). `effective_from_date` = **the outlet-local calendar date after
  the approval**. Used by: the `/sop` header, and R-11's before/after windows (dates before v2's
  `effective_from_date` count as "under v1", dates from it on as "under v2").

Why generation must read **latest**, not "in force": if generation read the in-force version, every proposal generated
between an approval and midnight would carry `generator.sop_version_id = v1` while R-09's guard compares against the
latest (v2), so each would be born with `SOP_CHANGED` and could never be approved; regenerating would give the same
dead result until midnight. Reading latest means "the pipeline reads v2" from the moment it ships, which includes "from
the next morning". Day-level attribution (what was done under which version) uses "in force". §11 Q-4 lets Rangga
overturn this.

**Applying the change (`planShip`, §0 items 3-5).**

| `content.target_step_id` | v{n+1} steps | `change.before` | `change.after` |
|---|---|---|---|
| an existing step id | v{n}'s steps with that one step replaced **in place** | the v{n} step, verbatim | `{ step_id: same, title: same as before, text: content.change_text, role: same as before }` |
| `null` (a new step) | v{n}'s steps + the new step **appended at the end** | `null` | `{ step_id: "p-" + proposal_id without hyphens, title: content.change_title, text: content.change_text, role: "staff" }` |

- The modified step keeps its title: `change_title` is a headline for the change ("Check the display every 30 minutes
  at peak"), not a step title. It is stored on the change record and shown as the card heading.
- Every other step is copied unchanged, in order.
- Text is copied as stored. It is already digit-masked, staff-name-scrubbed and SDP-redacted (R-08 step 8e) and is
  never re-sent to a model or to SDP by R-10.
- Conflicts (no write): latest SOP missing, or latest id ≠ `generator.sop_version_id`, or the target step id not in
  the latest SOP → `SOP_CHANGED`; adding to an SOP that already has 200 steps → `SOP_STEP_LIMIT` (new 409 code).

**Review date (§0 item 7).** At approval: `effective_from_date = addDays(localDateOf(now_ms, tz), 1)`;
`review_date = addDays(effective_from_date, content.review_after_days)`. The "after" window is then exactly
`review_after_days` days (`effective_from_date` … `review_date − 1`), and the review runs on `review_date`. The same
`review_date` is written to the SOP version's `change` and to the approved proposal's `content.review_date` (in the
same transaction, so every screen agrees). R-08 already made the review date code-owned ("Code, not the model, owns:
the review date", `R-08.md` §1), so recomputing it is not overriding the model. The audit entry records the new date
(dates are not person data).

**Concurrency.** Two owners (or two tabs) approving two different proposals generated on v1:
- R-09's transaction reads the latest SOP in-transaction; the second to commit either re-runs (Firestore retries on
  contention) and sees v2 → `SOP_CHANGED`, or its `tx.create("{outlet}:v2")` fails with `ALREADY_EXISTS` → the whole
  commit (proposal update, audits, SOP doc) is rejected → the store maps it to 409 `SOP_CHANGED`. Either way exactly
  one v2 exists and the other proposal stays `awaiting_owner`, now flagged "SOP has changed" by R-09's list.
- A double tap on Approve: R-09's idempotency returns `unchanged` with no write, so no second version.

**Status codes.** `GET /api/v1/sop` → **200** (`authedRequest` accepts 200; the empty "no SOP yet" state is a 200 with
`latest: null`, not an error). PR-2 adds one 409 code, `SOP_STEP_LIMIT`, to R-09's decision routes (client result
`conflict`); R-09's success codes are unchanged (200).

**Permissions.** `GET /api/v1/sop` requires `sop:diff` (owner and supervisor today, `lib/auth/rbac.ts`). Reason: the
payload includes the change list (metric, failure condition), which web spec §2 gives to owner and supervisor only;
`sop:read` also includes `staff` (post-MVP 1 "read current steps"). **No RBAC change.** The write needs
`proposals:approve` (owner only) through R-09's route, unchanged.

**What R-10 never does:** add any route that writes `sop_versions` (hard rule #9; the only writer is the owner-approve
transaction); change `getCurrentSop`; edit a `sop_versions` doc after creation (`tx.create`, never `set`/`update`); call
a model or SDP; build a diff view; build upload, export or a version picker (§0a).

## 2. Global constraints (every task inherits these)

- **Immutable versions:** a `sop_versions` doc is written once with `tx.create` and never updated or deleted by product
  code. The seed's `writeSopVersionIfAbsent` stays the only other writer (v1, once).
- **No person in any stored field:** a step's `role` is a job role; the change record has no uid, email, name, staff id
  or device id; audit entries carry `actor_role` only (hard rule #7).
- **Audit entries carry no text:** no step text, title, change title, metric description or failure condition in
  `details`. Ids, versions, dates and kinds only.
- **Logs:** never log step text or any model text. Store skips log `{ doc_id, error_class }` only (prefix
  `[sop-store]`).
- **Every Firestore read is outlet-scoped** (equality filter on `outlet_id`, docs with another `outlet_id` dropped).
- **Never write an explicit `undefined`:** build the SOP version and the updated proposal with every key present
  (`null` where empty) and parse with the schema before writing.
- **Responses** set `Cache-Control: private, no-store`.
- **No device-revealing id** in any response (the SOP data has none; `source_proposal_id` and `sop_version_id` are not
  returned by the read route either, see Task 4.1).
- **Model text and step text are rendered as plain text nodes, never through `t()` placeholders, never as HTML.**
- 360 px first; touch targets ≥ 48 px; copy only through `t(lang, key)`.
- **Read-only for R-10 (import, do not edit):** `lib/proposals/{service,view,contract,range,candidates,precheck,baseline,proposal-gate,wire-schema,constants}.ts`,
  `lib/firestore/proposal-store.ts`, `lib/agents/**` (except the one constant in Task 2.2), `config/**`,
  `lib/constraints/**`, `lib/auth/**`, `lib/http/**`, `lib/capture/**`, `lib/day/**`, `lib/debrief/**`,
  `lib/pipeline/**`, `scripts/seed.ts`, `app/capture/**`, `app/proposals/**` (except PR-2 Task 6.5), `private/**`.
  **Edited only as written here:** `lib/firestore/schema.ts` (Task 1, `sop_versions` section only),
  `lib/proposals/prompt.ts` (Task 2.1, one rule), `lib/agents/proposal-agent.ts` (Task 2.2, one constant),
  `lib/i18n/dict.ts` (Tasks 5.1, 6.5), `app/day/DayHeader.tsx` (Task 5.5, one link), and in PR-2 the R-09 files
  listed in Task 6.
- Every PR targets `develop`.

## 3. Review focus (failure modes no single happy-path test exercises)

1. **A second SOP write path.** Any route, service or script (other than the seed) that writes `sop_versions`, or any
   `set`/`update` on it. Pinned: Task 4.6 boundary test; Task 6 store test 6.S2 (`tx.create`, never `tx.set`).
2. **v2 built on the wrong base.** `planShip` reading a pre-transaction snapshot, or a stale latest. Pinned: 6.S1 (the
   SOP is read through `tx`), 3.T3 (id mismatch → `SOP_CHANGED`).
3. **Approved without a version / version without approval.** The proposal update and the SOP create not in one
   commit. Pinned: 6.S2 (all writes in the same `runTransaction`), 6.T4 (a planShip conflict writes nothing at all,
   not even the proposal).
4. **Lost race surfaces as a 500.** `ALREADY_EXISTS` from `tx.create` not mapped. Pinned: 6.S3.
5. **Step text silently truncated or rejected.** Pinned: 1.T2 (160/800 parse; 161/801 fail), 3.T6 (an 800-char
   `change_text` ships).
6. **Wrong "next morning".** Effective date computed in UTC or from the server clock's zone. Pinned: 3.T8 (approval at
   23:30 WIB and at 00:30 WIB, `Asia/Jakarta`).
7. **Review date left generation-relative on one surface.** Pinned: 6.T3 (proposal `content.review_date` ===
   `sop_version.change.review_date`).
8. **Seed docs broken by the schema change.** Pinned: 1.T1 (an R-08-era v1 doc without the new keys parses).
9. **Text in audit or logs.** Pinned: 6.T6 (sentinel in `change_text` absent from every audit and `console.*` call).
10. **Staff can read the change list.** Pinned: 4.T5 (staff → 403, device → 401).
