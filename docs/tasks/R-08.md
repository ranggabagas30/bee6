## 1. Architecture (decisions and why)

**One service function, two thin callers.** `lib/proposals/service.ts` `generateProposal(store, deps, input)` holds
every step. `POST /api/v1/proposals/generate` calls it now; P5 can call it later. Pure logic (`range`, `candidates`,
`precheck`, `proposal-gate`, `baseline`, `prompt`, `wire-schema`, `view`) is separate and unit-tested; the store is a
thin Firestore adapter; the model is an injected function. Same shape as R-06 and R-07.

**The flow is an explicit state machine in code; ADK runs exactly one step of it.**
```
validate range ─► load library + current SOP ─► reuse check ─► acquire outlet lease
  ─► read fact threads in range ─► plain-code evidence floor ──fail──► SUPPRESSED (insufficient_evidence), no model call
  ─► read constraints ─► build prompt + per-call schema ─► ProposalAgent (ADK, gemini-3.5-flash)   [attempt 1]
       ─► zod + plain-code proposal gate ──fail──► one retry with the failing rule codes as feedback  [attempt 2]
             ──fail again──► BLOCKED (fired rule)
       ─► model said no_proposal ──► SUPPRESSED (model_declined)
  ─► name scrub + SDP on model text ──fail──► 503, nothing written
  ─► transaction: re-read cited threads; drop stale ──< 2 items or < 2 dates──► BLOCKED (evidence_stale)
  ─► write AWAITING_SUPERVISOR proposal + audit ─► release lease
```
- **Why ADK runs only the model step (no tools):** the proposal is one structured decision over context we already
  hold. Giving the agent tools (fetch evidence, self-check) adds model round-trips, cost and nondeterminism for no
  gain, because plain code validates the output anyway and hard rule #10 forbids the model deciding evidence
  sufficiency. A self-check tool is exactly R-15's CriticAgent concept (post-MVP 1). ADK still earns its place: it is
  the named agent on the architecture slide, R-11 and R-15 reuse the same adapter, and the agent object is where a
  later Critic or tool slots in.
- **Why structured output via `responseJsonSchema`, not ADK's `outputSchema`:** `outputSchema` goes through ADK's
  own zod-to-genai `Schema` conversion (`simple_zod_to_json`), which is lossy; our per-call schema has dynamic enums
  (library ids, evidence aliases, SOP step ids) and `nullable`. R-05b already proved `responseJsonSchema` from
  `z.toJSONSchema` + `cleanJsonSchemaNode` on Vertex. We forward it through `generateContentConfig` and still
  validate the final text with our own zod schema (never trust a library's parse).
- **Evidence aliases, not thread ids, in the prompt.** Thread ids embed the device id
  (`unit_<device_id>_<window>:<n>`, R-06 §0 item 3). The prompt names candidates `E1..En`; code maps aliases back.
  Same pattern as R-05b's `T1/O1` aliases. Constraints are `C1..Cm` for the same reason (and so acknowledgement is
  checkable).
- **Evidence floor (plain code, before any model call): ≥ 2 fact threads on ≥ 2 distinct business dates.** Taken
  from `suff-v1`'s `evidence` rule (technical spec §8.15, thresholds confirmed by Rangga: "2 facts on 2 dates"),
  not invented. The backlog's "≥ 2 dated evidence items" alone would let two facts from one busy hour pass as a
  "pattern"; the confirmed suff-v1 wording closes that. Flagged in §11 Q-9 in case Rangga meant the looser reading.
  MVP 1 counts per thread (two paired devices inflate counts; the cross-device merge is post-MVP 1, backlog §6a).
- **The proposal gate is plain code** (`lib/proposals/proposal-gate.ts`, version `pgate-v1`), the proposal-level
  sibling of `lib/pipeline/gate.ts`: intervention in library, ≥ 1 rubric criterion in rubric, every cited alias known,
  ≥ 2 cited threads on ≥ 2 dates, target step exists (or `NEW`), every constraint acknowledged, metric category is one
  of the cited categories, text fits after redaction, cited threads still facts at commit. The model never decides any
  of these.
- **Code, not the model, owns:** the review date (`today + review_after_days`, model picks 7-28), the metric baseline
  (counted from facts), the censored-floor statement (a fixed `censored_floor: true` flag rendered by fixed copy on
  every proposal: technical spec says every proposal must state it, so no model sentence is trusted to), the
  evidence dates, and the status.
- **Status set** (technical spec §4.3): R-08 writes `suppressed` (too little evidence, or the model declined),
  `blocked` (the model proposed but the plain-code gate refused it twice, or evidence went stale), or
  `awaiting_supervisor`. `awaiting_owner`, `approved`, `rejected` are R-09's transitions; the enum includes them now

## 2. Global constraints (every task inherits these)

- **No device-revealing id in any response:** no `thread_id`, `device_id`, `question_id`, `line_id`. Evidence in a
  response is `{ date, start_hm, category, summary }`. Error messages too (`NotFoundError("outlet", "outlet")`, never
  an id). Test-enforced with a sentinel device id.
- **No text copied into a proposal from a thread** (technical spec §8.15): stored evidence refs are
  `{ thread_id, local_date, category, first_line_start_ms }` only. Summaries shown in the POST response come from the
  in-memory candidates; a reused proposal re-reads summaries live (and shows `null` if the thread has expired).
- **Every model free-text field is digit-run-masked, name-scrubbed, then SDP-redacted before it is stored or
  returned** (hard rule #3; technical spec §3.2 "any free text the model does return is redacted again before
  storage"). Redaction failure → 503, nothing written, lease released.

  staff name, a token. Model failures log `{ outlet_id, error_class, attempt }`. ADK's own logger is set to `ERROR`
  at module load (it writes through `console`); a test spies on `console.*` and asserts no sentinel text appears.

## 3. Review focus (failure modes no single happy-path test exercises)

1. **A fact the gate never made becoming evidence**: a non-fact, an `excluded_from_evidence` thread, a
   `supervisor_rejected` thread, a NON_WORK effective category, or a thread outside the range cited. Pinned: Task 3
   `selectCandidates` tests; Task 5 commit re-read (`evidence_stale`).
2. **The model deciding sufficiency**: a 1-fact case reaching the model. Pinned: Task 5 test asserts the model fake
   is never called (the backlog done-when).
3. **A hallucinated id passing**: an intervention, rubric id, alias or step id not offered. Pinned: zod enum + gate
   rules 1-6 (defence in depth), Task 3 tests.
4. **A device id leaking** via aliases mapping, the response, or an error. Pinned: Task 5/6 sentinel tests.
5. **Unredacted model text stored**: a phone number or a staff name in `change_text`. Pinned: Task 5 test with a
   fake redactor and a staff-name sentinel; redaction failure writes nothing.
6. **Two paid calls for one tap.** Pinned: Task 5 lease tests (held → 409, expired → reclaimed, released in
   `finally` even when the model throws).
7. **ADK logging the prompt.** Pinned: Task 4 console-spy test.
8. **A draft library reaching the demo.** Pinned: Task 1 (`allowDraft` false in production) and Task 6 route test
   (409 `LIBRARY_NOT_READY`). Since Q-2 closed the shipped files are `final`; this guard now only catches someone
   flipping a file back to `draft` or deleting it.
9. **An exhaustive `switch` on `label_source` / `fired_rule` without a default** breaking when R-06 PR-5 adds
   `supervisor_confirmed` / `supervisor_rejected` (R-06 §10 warning). Pinned: R-08 never switches on them; it only
   tests `status === "fact"`, `excluded_from_evidence !== true` and `label_source !== "supervisor_rejected"`.
10. **An owner-generated proposal skipping the supervisor** (v2, Q-10): any branch that sets `awaiting_owner` from
    the generate path, or reads `requested_by_role` to pick a status. Pinned: Task 5 test (owner request →

11. **A manual constraint stored unredacted, or carrying a name** (v2, Q-8): Pinned: Task 8 service tests (digit

### A.1 What the code actually accepts (re-checked against Task 1 and Task 2)

Each library file is parsed by `LibraryFileSchema` (Task 1). Each entry has **exactly** these keys; any other key
fails `.strict()`:

| Key | Rule | Where it goes |
|---|---|---|
| `id` | `^[a-z][a-z0-9_]{1,39}$`, unique in the file | the wire-schema enum (Task 4.2); stored in `content.intervention_id` / `content.rubric_criterion_ids` (Task 2) |
| `label_en` | 1-60 chars | prompt line `- <id>: <label_en>. <definition> <when_to_use?>`; the result card (Task 7) |
| `label_id` | 1-60 chars (Bahasa) | the result card in Bahasa |
| `definition` | 1-600 chars | sent to the model |
| `when_to_use` | optional, 1-600 chars | sent to the model, **interventions only** (the rubric prompt line prints only `<label_en>. <definition>`, Task 4.3) |

File level: `kind` (`interventions` \| `rubric`), `version` (positive int), `status` (`draft` \| `final`), `entries`
(1-30). The ids must match what the spec names (T-502); the draft files in Task 1 already fix them.

**Two things the request asked for that the schema has no field for, and how the example handles them:**
- **"What inputs an intervention needs"**: there is no `inputs` key. The example puts it in `when_to_use` as plain
  text ("Needs: ..."), which the model reads. Adding a structured `inputs` field is possible (one zod key + one
  prompt line) but nothing in the gate would check it, so I do not recommend it.
- **"An example proposal using it"**: there is no `example` key, and I recommend **not** adding one. A worked example
  inside the library becomes a few-shot sample the model tends to copy (same step, same wording), which works
  against "use only the facts given" (prompt rule 9). The examples in A.3 are shown *outside* the YAML, as the
  model's wire output, for human reading only.

### A.4 How this compares to Tiffany's scenario/control matrix

What was found in Tiffany's Google Sheet tabs (this session, PM's description; tech-lead did not open the sheet) is a
**scenario/control matrix**: rows per operational control, grouped by area codes (WKT, MSK, KLR, PRD, ...), each with
a trigger, an actor, the evidence that the control was done, a *Jalur gagal* (failure path) and a criticality level
(MERAH / ORANYE / KUNING / PUTIH). That is a different artifact:

- The **matrix** describes *what should already be checked* in the shop, control by control. It is closer to a
  richer, structured SOP than to a rubric.
- The **rubric** judges *one proposed change* ("is this change observable, owned, countable?"). The **intervention
  library** is the short menu of *kinds of change* the model may pick from. Both are about changing the SOP, not about
  running it, and both must be small (R-08 sends every entry in every prompt; 6 + 6 entries, ≤ 600 chars each).

**(a) Derive the rubric and library from the matrix.** Partly possible, not wholly:
- The matrix's column set maps well onto **rubric criteria**: "trigger" → `time_bound` / `unambiguous`, "actor" →
  `single_owner`, "evidence" → `observable` / `evidence_defined`, "Jalur gagal" → `failure_path`. That is a useful
  check that T-502's six are the right six, and Tiffany can phrase each definition as "a proposed step must state
  what the matrix's <column> would say for it".
- The four criticality levels are **not** good rubric criteria: they rank *how bad a control failure is*, not
  *whether a change is well-formed*. Their best use is later, as a priority signal (which category's facts a proposal
  should address first) or as the basis for a `no_new_incident_risk`-style criterion. That is post-MVP 1 scope.
- The "Jalur gagal" cells are good **source material** for writing `add_failure_path`'s definition and for judging
  examples, but they are per-control content, not intervention *types*. The six intervention types do not appear in
  the matrix at all.
- The matrix is Proofed-specific operational content, so anything copied from it is **real shop data** under hard
  rule #8: it must stay under `/private/` and never be committed.

**(b) Author a separate, small rubric + intervention document.** Six one-paragraph criteria and six one-paragraph
intervention types, each with Bahasa label, written generically (not Proofed-specific), so it can live in `config/`
in the public repo (Q-2 b) and be identical on demo and pilot.

**Recommendation: (b), using the matrix as Tiffany's reference while she writes it.** The matrix answers a different
question, so deriving the library from it would either produce Proofed-specific text that cannot be committed or
stretch control rows into "intervention types" they are not. A separate document of 12 short entries is about 1-2 h
of Tiffany's time; she can lift the matrix's trigger/actor/evidence/failure-path vocabulary into the six rubric
definitions and use its failure paths to sharpen `add_failure_path`, which gives most of the matrix's value with none
