**Goal:** turn a closed `LabelUnit` (built by R-05a's `windowing.ts`) into real `BuiltThread`s and
`GateDecision`s by calling Gemini 3.5 Flash-Lite with structured output, validating and sanitizing
that output, and persisting the result — wired end to end via a scheduled tick route, not a
per-segment Cloud Task.

**Architecture:** a `POST /api/internal/pipeline/tick` route, triggered by Cloud Scheduler every
2 minutes, processes one device at a time under a single-flight Firestore lease: load un-ledgered
segments → build windows/units (R-05a, unchanged) → call the label model → validate against a new,
strict wire schema → sanitize (category-scoped fields, staff-name scrub, SDP pass, length caps) →
feed the sanitized output into R-05a's already-frozen `buildThreads`/`evaluateGate` → persist threads
and questions → record labelled lines in a ledger → delete private (non-work) line text from the
source segments.

**Tech Stack:** `@google/genai` (Vertex mode, `gemini-3.5-flash-lite`, structured output via a
generated JSON schema), zod, the existing `lib/redact` SDP client, Firestore transactions.

**Spec:** `docs/specs/pipeline-and-agents.md` §E3 (T-301, T-303, T-304) · `docs/backlog.md` R-05b ·
`docs/specs/technical-specification.md` §6 (planned-stage detail, already flags the free-text risk
this plan fixes) · `docs/tasks/R-05a.md` (the frozen `LabelOutputSchema`/`buildThreads`/`evaluateGate`
contracts this task builds on top of and must not change the shape of).

**Decisions (tech-lead, 2 Oct, delegated by Rangga: "quality first, quick-win now, plan the full
version for later"):**
7. **`as_of_ms` skew estimate: newest-segment-only now; min-over-recent-segments deferred until real
   skew logs exist.** Newest-only can only err *early*: upload latency inflates the apparent skew
   (`received_at − device_end`), so `as_of_ms` lands at or before the device's true time, never after
   it (while the device clock offset is constant). The cost is extra label latency bounded by that
   segment's upload delay, which nothing consumes before the debrief (at the earliest 4 h after Mulai, technical spec §8.3). Min-over-recent is more
   precise but adds a failure mode newest-only does not have: if the device clock is corrected
   *backwards* mid-day (NTP resync, manual fix), the minimum comes from the pre-correction offset and
   puts `as_of_ms` *ahead* of the true device time, which closes windows early. Task 6 builds
   newest-only and logs both numbers every tick, so the eventual fix is chosen from data. See
   "Deferred" below.
8. **Staff-name scrub on the input unit, and explicit `fields` value rules.**
   - `buildThreads` (R-05a, `lib/pipeline/threads.ts`) copies each unit line's `text` verbatim into
     the stored thread's `lines`. Scrubbing only the model's output fields would therefore still
     store a spoken staff name in thread line text (hard rule #7). The unit's lines are scrubbed once,
     before the prompt is built, and **that same scrubbed unit** is the only unit passed to both
     `buildLabelPrompt` and `buildThreads` (Task 3 `scrubUnitLines`, Task 6 wiring).
   - `fields` values are primitive: an enum string, a boolean, or a capped string (default cap 80
     chars, `FIELD_STRING_DEFAULT_MAX`). Exactly two fixed-shape exceptions, because the spec already
     defines their shape (`docs/specs/pipeline-and-agents.md` T-304 example, `docs/specs/product-spec.md`
     "Fields") and Decision 4 already set their caps: `unmet_request: {item: string ≤ 40, reason:
     enum}` and `extracted_rules: string[]` (≤ 3 entries × ≤ 120 chars). No other nesting.
   - The response schema has **one flat `fields` object** whose optional properties are the union of
     every category's keys, no `anyOf`. The per-category key allowlist (yaml `categories.*.fields`)
     and every per-key value rule are enforced **in code** by the sanitizer, as drop-the-key, never a
     throw. Invalid values are dropped, never truncated (truncating "never refund" changes meaning).
   - **Rejected: 12 per-category zod schemas / a discriminated union in the response schema.** It
     compiles to a large `anyOf`, which Vertex's structured-output subset may reject with a 400 or
     handle poorly, and it duplicates a check the sanitizer already does deterministically in code.

## Review focus (eight likely failure modes the spec doesn't test for directly — each gets a task below)
1. **A hallucinated or model-echoed staff name reaching stored thread text.** The model sees redacted
   input but can still *generate* a name from context (e.g. inferring "Dina" from a Bluetooth device
   name mentioned in speech, or just hallucinating one). → Task 3 (scrub on input via `scrubUnitLines`
   AND on output via `sanitizeLabelOutput`).
2. **An out-of-enum or missing category/confidence reaching the gate as if valid.** R-05a's gate
   already has defense-in-depth here, but the model is the first real source of this kind of bad input
   — a loose wire schema would make the gate's own hardening the *only* defense. → Task 2 (strict wire
   schema rejects before the gate is ever called).
3. **A segment that arrives late (after the device was briefly offline) being silently skipped or
   labelled twice.** The TSD's own G-1 finding. A naive "has this unit been processed" check would
   miss lines that arrive into an *already-processed* unit. → Task 5 (per-line ledger, not per-unit).
4. **The label call succeeding with malformed JSON or a zod failure becoming a crash instead of a
   question.** CLAUDE.md requires every model-output failure to become a debrief question, never a
   silent fact and never an unhandled error. → Task 4 (one retry, then `failed` → exactly one question
   per unit, never zero and never more than one).
5. **Two tick invocations overlapping for the same device** (Scheduler firing before the previous tick
   finished, or a manual "process now" task colliding with the scheduled one) **corrupting which
   thread is "open."** → Task 6 (the lease: a Firestore `create()` on a lease document with an expiry,
   so a second concurrent tick for the same device fails to acquire and simply skips that round).
6. **A spoken staff name stored through the thread's own line text, not the model's output.**
   `buildThreads` copies unit line text verbatim into the stored thread. If the route scrubs a copy
   for the prompt but passes the *original* unit to `buildThreads`, every output-side test still
   passes and the name is stored anyway. → Task 3 (`scrubUnitLines`, with a test proving the scrub is
   load-bearing) + Task 6 (one scrubbed unit feeds both the prompt and `buildThreads`; e2e test).
7. **A response schema Vertex rejects, or a `fields` value that slips past the category's rules.**
   `z.toJSONSchema` can emit `anyOf` (e.g. for `.nullable()`), `$ref`/`$defs`, or
   `additionalProperties`. → Task 2 (flat `fields` object from `FIELD_SHAPES`; a test walks the whole
   generated schema for forbidden keywords) + Task 3 (per-key validate-and-drop against the
   category's allowlist).
8. **`as_of_ms` landing *ahead* of the device's true time**, which closes windows early and splits
   units. → Task 6 (`deriveAsOfMs`, newest segment only; a test proves a late upload moves `as_of_ms`
   earlier, never later).

## Task 3: sanitizer (category-scoped fields, staff-name scrub, SDP pass)

**Files:**
- Create: `lib/pipeline/label/scrub.ts` — `scrubStaffNames(text: string, staffNames: readonly
  string[]): string`.

  CategoriesConfig, staffNames: readonly string[]}): Promise<LabelOutput>` (the R-05a-frozen type).
- Create: `lib/pipeline/label/sanitize.test.ts`

**Interfaces:**
- Consumes: `LabelOutputSchema` (R-05a, `lib/pipeline/threads.ts`) as the final output contract —
  `sanitizeLabelOutput`'s return value must always `LabelOutputSchema.parse()` successfully.
- Consumes: the existing SDP client from `lib/redact` (same module R-04 already uses) for the batched
  pass over the model's free-text fields.
- Produces: `scrubStaffNames` — word-boundary, case/accent-insensitive replacement of any staff name
  with `[STAFF]`. Over-redaction (e.g. a name that's also a common word) is accepted by design.
- Produces (`scrub.ts`): `scrubUnitLines(unit: LabelUnit, staffNames: readonly string[]): LabelUnit` —
  returns a **new** unit whose every `lines[i].text` has been passed through `scrubStaffNames`; every
  other property (`unit_id`, `window_ids`, each line's `line_id`/`start_ms`/`end_ms`, line order) is
  unchanged; the input unit is never mutated. Decision 8: this runs before `buildLabelPrompt`, and its
  return value is the only unit passed to both `buildLabelPrompt` and `buildThreads` for that call.
- Consumes: `buildFieldSchemas(config).zod` (Task 2) for per-key `fields` validation.
- `sanitizeLabelOutput` processing order, per thread: (1) drop `fields` keys not in
  `config.categories[category].fields` → (2) drop keys whose value fails `buildFieldSchemas(config)
  .zod[key].safeParse` → (3) digit-run replacement → (4) `scrubStaffNames` → (5) one batched SDP call
  per unit → (6) over-length fallback template for `summary`. Validation (1–2) runs on the model's raw
  values, so replacement tokens added in (3–5) can never cause a drop. Free-text strings that go
  through (3–5): `summary`, `runner_up.why_not`, `fields.unmet_request.item`, every
  `fields.extracted_rules[]` entry. Enum and boolean values are not sent to SDP.
