## 0. Findings and blockers (read first)

1. **Blocked on R-09 PR-A and R-10 PR-1 merging** (imports below). No other blocker.
2. **`reviews` and `outcomes` are stubs** in `lib/firestore/schema.ts` (`outlet_id` + one id, "filled in R-11").
   Nothing reads them (checked). R-11 defines both shapes (Task 1).
3. **One Scheduler job per review date is the wrong mechanism.** Creating a Cloud Scheduler job per SOP version would
   need the app to call the Scheduler admin API (new IAM, new failure mode, cleanup). Decision (§1 "Trigger"): **one
   fixed daily job** (09:00 Asia/Jakarta) calls `POST /api/internal/reviews/run`, which reviews every shipped change
   whose `review_date` is today **or earlier** (catch-up if a run was missed) and has no review yet. "Fires without
   anyone pressing anything" holds, and it is idempotent.
4. **"ReviewAgent" as a Gemini agent vs plain code.** The architecture names a ReviewAgent on Gemini 3.5 Flash. The
   numbers it compares are plain counts (R-08 §9: "the before/after count is plain code over threads"). Default
   (§1 "Suggestion", §11 Q-1): **the suggested verdict is plain code** (rule `rev-v1`), deterministic and testable, in
   the spirit of hard rule #10 ("AI suggests, plain code filters, humans decide": here the humans decide on plain-code
   numbers). A model-written rationale is the option in Q-1 (+1.5 h). The module keeps the name "review" and the README
   must not claim a Gemini ReviewAgent unless Q-1 (b) is chosen.
5. **The browser cannot call the scheduler's route.** `/api/internal/*` is OIDC-only (`lib/http/oidc.ts`); a judge's
   browser has a Firebase token. "Fast-forward calls the same route" is met as **the same service function**
   (`createReview`) behind two thin routes: the OIDC internal route and a **demo-only** user route that returns 404
   unless `DEMO_MODE === "true"` **and** the outlet's `project_kind === "demo"` (`OutletSchema.project_kind` exists).
   Matches the 7 Oct decision "only inject `now` in R-05a/R-11".
6. **A fast-forward on the demo measures whatever threads exist in the windows.** The "after" window is
   `effective_from_date … review_date − 1`, which on a fast-forward lies in the future, so it is normally empty and the
   suggestion is `not_enough_days`. A meaningful demo needs fixture threads dated in the after window; that is R-12's
   seeding job (its fixture writer writes Firestore directly on the demo project). Recorded in §8, not built here.
7. **"Memory" has no reader today.** No code reads outcomes (the ProposalAgent prompt has no outcome section). Default
   (§11 Q-3): R-11 stores outcomes with an explicit `in_memory` flag (`false` for "unknown"), shows confirmed outcomes
   on the `/sop` change card, and exports one pure filter `memoryOutcomes()` that any future reader must use. Feeding
   outcomes into the ProposalAgent prompt is the Q-3 option.
8. **A "revert" verdict must not touch the SOP** (hard rule #9: SOP changes only through proposals). Default (§11
   Q-4): every verdict is recorded only; the card tells the reader that undoing the change needs a new proposal.
9. **New env var `REVIEW_RUN_AUDIENCE`** (the review route's own public URL; never derived from the request, same rule
   as `PIPELINE_TICK_AUDIENCE`). `CLAUDE.md` §6 lists env names; the PM adds it there (governance file).
10. **Effort: 6.0 h** against the backlog's 4 h (**+2.0 h**). Why, and the cut list, in §9.

## 1. Architecture (decisions and why)

**Same split as R-08/R-09/R-10: pure planner, thin service, thin store, thin routes.**
- `lib/reviews/metric.ts`, `verdict.ts`, `plan.ts`: pure (windows, counting, the `rev-v1` suggestion, the verdict
  state machine, expiry, the review and outcome docs). No I/O.
- `lib/reviews/service.ts`: `runDueReviews`, `createReview`, `listReviews`, `decideVerdict`, `fastForwardReview`.
- `lib/firestore/review-store.ts`: reads (outlets, versions via `firestoreSopStore`, the proposal, sessions, threads,
  reviews) and three transactions (create review, record verdict, expire).
- Four routes: `POST /api/internal/reviews/run` (OIDC), `GET /api/v1/reviews`, `POST /api/v1/reviews/{version}/verdict`,
  `POST /api/v1/reviews/fast-forward` (demo only).
- `/reviews` page; one outcome line added to R-10's `/sop` change card.

**Trigger (§0 item 3).** Cloud Scheduler job `review-run`, `0 9 * * *`, time zone `Asia/Jakarta`, `POST` to
`/api/internal/reviews/run` with an OIDC token as `TASKS_INVOKER_SA`, audience `REVIEW_RUN_AUDIENCE`. One job per
project (demo and pilot), created by dev-ops. Per run, per outlet (all outlets in the project, isolated by try/catch so
one bad outlet never blocks the rest):
1. `today = localDateOf(now_ms, outlet.timezone)`.
2. **Create** a review for every shipped change (`source: "proposal"`, non-null `change`) with
   `change.review_date ≤ today` and no review doc yet.
3. **Expire** every review still `awaiting_supervisor` / `awaiting_owner` with `confirm_by_date < today`: status
   `unknown`, and an outcome `{ verdict: "unknown", in_memory: false }` (the done-when).

**Ids.** `review_id = outcome_id = sop_version_id` (`"{outlet}:v{n}"`): one review per shipped change, idempotent by
`tx.create`. Routes address a review by **version number** (`/api/v1/reviews/2/verdict`) and build the id from
`claims.outlet_id`, so a cross-outlet id cannot even be expressed and no colon goes in a URL.

**Windows (plain code).**
- **Before** = the source proposal's `range` (`from_date … to_date`), with `to_date` clipped to
  `effective_from_date − 1` (always already true: the range ends on or before the generation date, which is before the
  effective date). This is the evidence period the change was proposed from, re-counted at review time (so a fact a
  supervisor rejected after generation no longer counts).
- **After** = `effective_from_date … review_date − 1` (exactly `review_after_days` days, `R-10.md` §1).
- **Count** = facts whose effective category equals `metric.category`, selected with R-08's **own**
  `selectCandidates` (fact, not excluded, not `supervisor_rejected`, not NON_WORK, attributed business date in the
  window, discarded sessions excluded). Imported, not re-implemented.
- **Days captured** = distinct business dates in the window that have at least one non-discarded capture session
  (any device), plus any date a counted fact is attributed to. A day nobody captured is not a "zero-problem" day.
- **Rate** = `count / days_captured` (computed for display and the suggestion; the doc stores counts and days).
  "Weekdays" in T-509 falls out of this: days without capture are not in the denominator; captured weekend days are.

**Suggestion (`rev-v1`, plain code, §0 item 4).** Constants: `MIN_DAYS_PER_WINDOW = 2`, `CHANGE_THRESHOLD = 0.2`.
In order:
1. `before.days_captured < 2 || after.days_captured < 2` → `{ verdict: null, reason: "not_enough_days" }`.
2. `before_rate === 0` → `{ verdict: null, reason: "no_baseline" }`.
3. `change_ratio = (after_rate − before_rate) / before_rate`; `improvement = direction === "decrease" ? −change_ratio : change_ratio`.
4. `improvement ≥ 0.2` → `worked` (`improved`); `improvement ≤ −0.2` → `revert` (`worsened`); else `revise`
   (`no_clear_change`).
The free-text `failure_condition` is shown to the humans next to the numbers; plain code does not interpret it.

**Verdict state machine (the only legal moves; everything else is a 409):**
```
awaiting_supervisor ──supervisor verdict──► awaiting_owner ──owner verdict──► confirmed  (+ outcome, in_memory: true)
        │                                         │
        └──────── daily run, confirm_by_date < today ──────► unknown  (+ outcome "unknown", in_memory: false)
```
- Supervisor picks worked / revise / revert (any, not bound to the suggestion), optional reason.
- Owner sees the supervisor's verdict and picks (same or different), optional reason. **The owner's verdict is the
  outcome** (final say, mirroring R-09's approval order).
- `confirm_by_date = review_date + REVIEW_CONFIRM_DAYS (7)`. A verdict on or before it is accepted; after it the route
  answers 409 `EXPIRED` and the next daily run writes `unknown`.
- Same actor, same verdict again → `unchanged` (200). Different verdict from the same actor after deciding → 409
  `ALREADY_DECIDED`. Owner before the supervisor → 409 `NOT_YET_REVIEWABLE`. Anything on `confirmed` / `unknown` →
  409 `ALREADY_DECIDED` / `EXPIRED`.
- An outlet with no supervisor account cannot confirm, so its reviews end `unknown` (same known limit as R-09 E25).

**Reason (T-510 "reason field").** Optional, trimmed 3..300 characters when given, redacted with R-09's
`redactUserText` (digit mask → staff-name scrub → SDP) before storage; SDP down → 503, nothing written. Stored on the
review only, **never copied into the outcome** (memory carries verdicts and numbers, not text).

**Fast-forward (§0 item 5).** `POST /api/v1/reviews/fast-forward` (owner or supervisor; `reviews:verdict`):
- 404 `NotFoundError("route", "route")` unless `process.env.DEMO_MODE === "true"` **and** the caller's outlet has
  `project_kind === "demo"` (double guard; the pilot project never sets `DEMO_MODE`).
- Picks the **lowest-version** shipped change of the outlet that has no review yet (any `review_date`, including
  future), and calls the same `createReview` as the daily run with `simulated: true`. None → 409 `NOTHING_TO_REVIEW`.
- `simulated: true` is stored on the review and the outcome and shown on every screen as "Simulated time".
- It never moves any clock: windows are fixed by dates, so "as of the review date" needs no time injection beyond
  choosing the change regardless of `review_date ≤ today`.

**Overlapping change notice.** If a later version of the same outlet has `effective_from_date ≤ review_date − 1`, the
after window mixes two changes: `notices.overlapping_change = true` and the card says so. The suggestion is still
computed (humans judge).

**Status codes (checked against `lib/auth/client/api.ts` `authedRequest`: 200 and 201 are `ok`).** All user routes
answer **200** on success (including `unchanged`); internal route 200 with a summary. Errors: 400 bad JSON, 401, 403,
404, 409 (`EXPIRED`, `ALREADY_DECIDED`, `NOT_YET_REVIEWABLE`, `NOTHING_TO_REVIEW`), 422 `invalid_body`, 503.

**Permissions.** New `reviews:read` (owner, supervisor) for the list; `reviews:verdict` (owner, supervisor; exists)
for the verdict and fast-forward routes; the slot (supervisor / owner) is taken from `claims.role` on the server,
never from the body.

**What R-11 never does:** write or edit `sop_versions` or `proposals` (hard rule #9; a revert is recorded only); call a
model (default); move a clock; copy reason text into outcomes; read or return thread text, thread ids or device ids.

## 2. Global constraints (every task inherits these)

- **No person in any stored field:** verdict slots are roles by position (`supervisor_verdict`, `owner_verdict`);
  audit `actor_role` only (`system` for the daily run). No uid, email, name, staff id or device id (hard rule #7).
- **Every reason is redacted before storage** (hard rule #3) via `redactUserText`; failure → 503, nothing written.
- **Audit entries and logs carry no text:** no reason, change title, metric description, failure condition or step
  text. Logs: `[review] created|decided|expired|refused { outlet_id, version, result | code }` only.
- **No device-revealing id in any response:** responses carry `version`, dates, counts and text fields copied from the
  SOP change; never `thread_id`, `device_id`, `source_proposal_id` or `sop_version_id`.
- **Every Firestore read is outlet-scoped**; malformed docs skipped and logged `{ doc_id, error_class }` only
  (prefix `[review-store]`).
- **Never write an explicit `undefined`**; build docs with explicit `null`s and parse before writing.
- **`tx.create` for reviews and outcomes** (write-once); reviews are updated only by the verdict and expiry
  transactions; outcomes are never updated.
- **Responses** set `Cache-Control: private, no-store`.
- **Read-only for R-11 (import, do not edit):** `lib/proposals/**` (imports `selectCandidates`), `lib/sop/**` (imports
  `latestSop`), `lib/firestore/{proposal-store,sop-store,constraint-store,proposal-review-store}.ts` (except Task 7's
  one store method in `sop-store.ts`), `lib/redact/**`, `lib/http/**` (imports `verifyInternalOidcToken`),
  `lib/day/**`, `lib/capture/**`, `lib/pipeline/**`, `lib/agents/**`, `config/**`, `scripts/**`, `app/proposals/**`,
  `app/capture/**`, `private/**`. **Edited only as written here:** `lib/firestore/schema.ts` (Task 1, the `reviews` and
  `outcomes` stubs only), `lib/auth/rbac.ts` (+test, Task 1.3), `lib/i18n/dict.ts` (Task 6.1), `app/day/DayHeader.tsx`
  (Task 6.6, one link), and in Task 7 `lib/sop/contract.ts`, `lib/sop/service.ts`, `lib/firestore/sop-store.ts`,

- 360 px first; touch targets ≥ 48 px; copy only through `t(lang, key)`; model/SOP text and reasons rendered as plain

  })
  .strict();

  .object({
    ...withOutlet,
    review_id: z.string().min(1), // = doc id = sop_version_id
    sop_version_id: z.string().min(1),
    version: z.number().int().min(2),
    source_proposal_id: z.string().uuid(),
    change_title: z.string().min(1).max(160),
    step_id: z.string().min(1),
    intervention_id: z.string().min(1),

    failure_condition: z.string().min(1).max(480),
    effective_from_date: dateString,
    review_date: dateString,

    after: ReviewWindowSchema,

      .object({
